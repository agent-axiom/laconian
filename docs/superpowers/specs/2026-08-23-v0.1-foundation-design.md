# Laconian v0.1 Foundation Design

**Date:** 2026-08-23

**Status:** Approved direction; written specification awaiting maintainer review

**Scope:** The first end-to-end implementation slice for the public project, the portable `if` skill, and its benchmark

## 1. Objective

Laconian is a public philosophy project and an open benchmark for concise agent answers. Its reference skill, `if`, promises the shortest complete answer: an answer may become shorter only while it remains correct, safe, clear, useful, natural, and compliant with the user's request.

The first implementation slice must make that promise inspectable rather than market it with unsupported savings claims. It will provide:

- one portable Markdown-only skill at `skills/if/SKILL.md`;
- a runnable, provider-neutral benchmark skeleton;
- four transparent comparison arms: ordinary agent, `Answer concisely.`, pinned `caveman`, and `if`;
- separate activation and response-quality evaluation suites;
- raw, replayable run records and a report that never rewards failed answers for being short;
- an English source README plus Russian, Simplified Chinese, Modern Greek, Italian, and reconstructed Laconian Doric editions.

## 2. Decisions and assumptions

- The repository and public project name are `laconian` and Laconian.
- The skill identifier and directory name are `if`.
- `skills/if/` contains only `SKILL.md`: no scripts, references, assets, dependencies, or UI metadata.
- The benchmark package is `laconian_eval` and requires Python 3.11 or newer.
- The core benchmark is provider-neutral. The first live adapter targets OpenAI; tests use deterministic fake and replay adapters and require no network or API key.
- Benchmark cases use YAML. Pydantic validates case, manifest, raw-result, and judge-result schemas; PyYAML handles serialization.
- The command is `laconian`; no executable named `if` is created.
- Code and `skills/if/SKILL.md` use Apache-2.0. Documentation, eval cases, and published benchmark results use CC BY 4.0.
- English is the source language for public documentation. Translations link to the English source and may be updated in later commits when the source changes.
- `.idea/` is user-owned local state. It remains untouched and is ignored by the repository.

## 3. Approaches considered

### A. Documentation-first scaffold

Publish the skill, README files, philosophy, methodology, and case schema before writing a runner.

This is the fastest route to a visible repository, but it cannot prove that the schema, comparison arms, raw-result format, and reporting rules work together. Methodology errors would be discovered after the public contract had already hardened.

### B. Vertical walking skeleton — selected

Build one thin, runnable path through packaging, case loading, four comparison arms, one live provider adapter, raw recording, deterministic checks, optional semantic judging, and report generation. Start with 12 semantic response scenarios, each represented in Russian and English (24 case records), plus four activation scenario types in both languages (eight records). Then expand the same contracts to 100 or more response records.

This takes slightly longer than a documentation-only launch, but tests the architecture before scale. It also produces a useful negative result if `if` fails to outperform a simpler instruction.

### C. Full v0.1 implementation in one pass

Create 100 or more cases, three live provider adapters, installation checks in three agent hosts, all translations, human preference studies, and final benchmark results before the first release.

This maximizes initial completeness but couples too many unvalidated decisions. A schema or scoring correction would require rewriting cases, adapters, and reports together.

## 4. Release boundaries

### Included in the first walking skeleton

- repository hygiene, licenses, contributor-facing project files, and CI;
- the canonical `if` skill;
- English README and five translated editions;
- 12 semantic response scenarios represented in RU and EN (24 case records), covering direct answers, code, exact values, structured output, uncertainty, and safety caveats;
- four activation scenario types represented in RU and EN (eight records), covering explicit invocation, a natural-language brevity request, an ordinary programming `if`, and a request for a detailed fixed-format explanation;
- the provider protocol, fake adapter, replay adapter, and OpenAI adapter;
- baseline manifests, raw JSONL output, deterministic checks, semantic-judge interface, and Markdown reports;
- unit and end-to-end tests using fake/replay data.

### Deferred until the skeleton is stable

- expansion to at least 100 cases;
- Anthropic and local-model adapters;
- real-host activation runners for Codex, Claude Code, and Gemini CLI;
- repeated public benchmark runs and human preference evaluation;
- cold-versus-warm cache experiments;
- release `v0.1.0` and public efficiency conclusions.

### Explicit non-goals for v0.1

- an MCP server, web service, browser extension, background telemetry, or hosted leaderboard;
- multiple brevity modes in `if`;
- automatic rewriting of other skills or prompts;
- a single composite score;
- any fixed percentage-savings claim.

## 6. The `if` skill contract

### Discovery and activation

The frontmatter description must be short enough for skill discovery and discriminating enough to avoid the English conjunction and programming keyword. Automatic activation is appropriate only when the user asks for a concise, laconic, no-fluff, or to-the-point answer. Explicit invocation always loads the skill, but explicit requirements for detail, pedagogy, structure, or length remain authoritative.

Ordinary prose containing “if” and source code containing the `if` keyword are negative activation examples. A request such as “be concise but explain every migration step” is not a contradiction: the agent retains every requested step and removes only redundancy.

### Response behavior

The skill performs semantic editing, not primitive speech. It first determines the complete answer and then removes material in this order:

1. greetings and acknowledgements;
2. restatement of the request;
3. process narration that the user did not request;
4. repeated conclusions and obvious explanations;
5. decorative headings, redundant lists, and weak transitions;
6. caveats that cannot change the user's decision.

It stops before the next deletion would reduce correctness, safety, requirement coverage, material facts, uncertainty, practical sufficiency, clarity, tone, or natural grammar.

### Exact and structured content

The compression pass must not alter code, commands, error messages, URLs, identifiers, versions, numbers, quotations, or machine-readable structures when their exact form is required for the answer. A direct user request to transform such content takes precedence; for example, “change port `8080` to `9090`” is allowed.

For JSON, YAML, tables, and other schemas, the skill preserves every required key, item, order, and format. It may omit only content that the schema and user request make optional, and it does not add surrounding prose unless needed.

### Portability

The skill is written in English, uses no platform-specific tool names, grants no permissions, performs no external actions, and depends on no other file. Its observable behavior is evaluated separately from installation mechanics.

## 7. Benchmark design

### Separate evaluation suites

The project has two suites because they answer different questions:

1. **Activation suite:** Should a host select `if` for this user request? The smoke suite stores expected trigger decisions. Initial proxy routing results are clearly labeled as proxy results; public host-compatibility claims require execution in the named host.
2. **Response suite:** What happens when each comparison instruction is deliberately applied? This suite bypasses automatic skill selection and injects each arm at the same instruction location.

Activation accuracy is never folded into response quality or token savings.

### Comparison arms

- `baseline`: no added brevity instruction;
- `concise`: exactly `Answer concisely.`;
- `caveman`: an offline snapshot of the default full Caveman skill, pinned to upstream commit `781c384cafc28d7ca392014dbab569f985b5b2fd` and accompanied by its MIT attribution;
- `if`: the repository's exact `skills/if/SKILL.md` bytes.

Every raw record stores the arm text hash. The runner appends the arm content to the same stable system-instruction slot for every non-baseline run. The baseline uses the identical prompt without that appended content. User prompts, tool availability, sampling settings, model, and repetition index remain identical.

### Case schema

Each response case contains:

```yaml
id: retry-post-001
locale: ru
category: coding
prompt: "..."
hard_constraints:
  required_literals: ["POST"]
  forbidden_literals: []
  required_json_keys: []
  max_sentences: 2
semantic_rubric:
  required_facts:
    - "POST may be non-idempotent"
    - "retries may duplicate operations"
  material_warning: null
```

Fields that do not apply use empty collections or `null`; the schema rejects unknown fields, duplicate IDs, unsupported locales, impossible limits, and empty prompts.

Activation cases contain `id`, `locale`, `prompt`, `expected_activation`, and a short rationale for maintainers. Rationales are never shown to the routing model.

### Run manifest and raw records

A run manifest fixes:

- provider and exact model identifier;
- generation settings and supported seed;
- case files and comparison arms;
- repetition count and randomized arm-order seed;
- instruction placement;
- timeout and retry policy;
- optional price snapshot;
- runner and schema versions.

The runner emits one JSONL record per attempt. Each record includes run ID, case ID, arm, repetition, prompt and instruction hashes, model/provider identifiers, settings, timestamps, latency, output text, provider token fields, cache fields when available, finish reason, error classification, and retry lineage. Environment-variable names may be recorded; secret values never are.

Transient provider failures may be retried twice. Every attempt remains in the raw file. Denials, timeouts, malformed responses, and exhausted retries are results rather than missing rows.

### Scoring order

1. Validate that a raw record matches the manifest and case.
2. Apply deterministic checks for exact literals, forbidden literals, sentence limits, and structured-output validity.
3. Apply an optional semantic judge to responses that pass deterministic checks.
4. Mark task success before calculating brevity metrics.
5. Compare output length only on matched case/repetition pairs that pass for both compared arms.

The semantic judge receives the prompt, rubric, and response without the arm name. It returns structured pass/fail fields, defect codes, and short evidence. Judge results remain separate from raw model output, and reports disclose the judge provider/model and prompt hash. Smoke tests use replayed judge results; public claims require a frozen judge protocol and human audit sample.

### Reported metrics

Reports show separate values rather than a composite rank:

- deterministic pass rate;
- semantic task-success rate;
- exact-value violations;
- format violations;
- median and distribution of output tokens or characters;
- paired output reduction among mutually passing responses;
- input, output, cached-input, and total provider tokens when available;
- price-estimated cost only when the manifest supplies an explicit dated price snapshot;
- latency, provider errors, and retry counts;
- confidence intervals for public repeated runs.

A failed answer cannot win a brevity comparison. Cross-provider cost and cache numbers are shown separately because providers expose different accounting semantics.

### Hypothesis reporting

The primary comparison is `if` versus `Answer concisely.`. The ordinary and Caveman arms provide context, not an easier marketing baseline. A completed benchmark may confirm, reject, or leave the hypothesis inconclusive. Release readiness depends on reproducibility and disclosure, not on forcing a positive result.

## 8. Data flow and CLI

```text
manifest
  -> validate cases and arms
  -> create deterministic run plan
  -> call provider or replay fixture
  -> append raw attempt record
  -> apply deterministic checks
  -> optionally attach blind semantic judgment
  -> aggregate only eligible comparisons
  -> write Markdown report and machine-readable summary
```

The CLI exposes four narrow commands:

```text
laconian validate <case-or-manifest-path>
laconian run <manifest-path> --results-root <directory>
laconian score <raw-jsonl-path> --output <directory>
laconian report <scored-jsonl-path> --output <report-path>
```

`run` creates a uniquely named child under `--results-root` and never overwrites an existing run directory. `score` and `report` are deterministic for identical inputs and also refuse to overwrite existing outputs. Interrupted runs resume only when the manifest hash matches; completed case/arm/repetition keys are skipped and recorded in the run log.

## 9. Error handling and safety

- Configuration and schema errors fail before any provider call and report the exact field path.
- Provider authentication errors stop the run without retrying.
- Rate limits, timeouts, and transient server errors use bounded retry with recorded backoff metadata.
- Raw output is append-only during a run and written with flush-and-fsync boundaries so partial runs remain inspectable.
- API credentials come only from environment variables or provider-native credential stores and are redacted from errors.
- Benchmark prompts are untrusted data. They cannot change runner configuration, filesystem targets, provider credentials, or scoring rules.
- Generated model text is never executed as code or a shell command.
- Output directories must be inside the selected benchmark-results root; existing run directories are not overwritten.

## 10. Documentation and historical framing

The English README leads with the promise “the shortest complete answer,” then explains the quality gate, installation, the four-arm comparison, current project status, and how to reproduce published runs. It does not lead with a savings percentage.

The origin story is attributed precisely: Plutarch, writing centuries after Philip II, preserves an anecdote in which Philip threatens Laconia and the Laconians answer with the Doric word `αἴκα` (“if”). The README does not present the exchange as a surviving contemporary letter, does not use the expanded viral threat, and does not claim that Philip never entered Laconia.

Translation files use this language navigation:

| Language | File |

| Русский | `README.ru.md` |
| 简体中文 | `README.zh-CN.md` |
| Ελληνικά | `README.el.md` |
| Italiano | `README.it.md` |
| Laconian Doric (reconstructed) | `README.grc-x-laconian.md` |

The Laconian Doric edition is explicitly labeled an experimental reconstruction in a fragmentarily attested Ancient Greek dialect. Modern software terms may remain code-formatted English or receive transparent transliterations. It is not described as an authentic ancient text, and expert review is invited.

## 11. Test strategy

Implementation follows test-driven development. The initial suite must prove these observable contracts:

- valid and invalid YAML cases produce stable validation results;
- duplicate case IDs and unknown schema fields are rejected;
- comparison arms are loaded byte-for-byte and hashed;
- the programming keyword `if` is a negative activation case;
- explicit `/if` and natural brevity requests are positive activation cases;
- a detailed or fixed-format request preserves its requested detail;
- exact literals, numbers, URLs, code, commands, and required JSON keys survive scoring checks;
- a deterministic failure makes a response ineligible for brevity victory;
- the runner records every arm for every planned case and retains provider failures;
- retry attempts are bounded and linked;
- resume never mixes manifests or duplicates completed run keys;
- raw records contain no configured secret values;
- fake/replay end-to-end execution produces a stable machine summary and Markdown report;
- all six README files link to one another and the reconstructed-language warning is present;
- `skills/if/SKILL.md` passes the Agent Skills structural validator and contains no sibling artifacts.

CI runs formatting, linting, type checking, unit tests, the replay end-to-end test, skill validation, and public-contract checks on supported Python versions.

## 12. Walking-skeleton completion criteria

The first slice is complete when:

- a fresh checkout installs the `laconian` command using documented steps;
- the standalone `skills/if/SKILL.md` validates and can be copied without any other project file;
- all 24 response records and eight activation records validate;
- replay mode runs all four arms and generates raw, scored, and report artifacts;
- the OpenAI adapter passes mocked contract tests and a documented optional live smoke command exists;
- deterministic hard failures cannot improve a brevity result;
- licenses and Caveman attribution are correct;
- English and five translated README editions are present with consistent navigation;
- CI passes without network access or provider credentials;
- no benchmark percentage claim appears in public documentation.

This slice validates the architecture. It does not constitute the 100-case public benchmark or a claim that `if` outperforms another arm.
