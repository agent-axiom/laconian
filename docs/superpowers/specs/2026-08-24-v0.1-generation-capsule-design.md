# Laconian v0.1 Self-Contained Generation Capsule Design

**Date:** 2026-08-24

**Status:** Written specification awaiting maintainer review

**Scope:** PR 3: prepare, execute, resume, verify, and seal a self-contained generation capsule

## 1. Decision

PR 3 replaces the earlier statistics-first design. It creates a trustworthy source of raw
benchmark evidence before adding inference, automated judging, human review, or public claims.

The selected boundary is a layered artifact model:

1. PR 3 seals an immutable generation capsule.
2. PR 4 creates scoring and inference attachments that reference the generation-capsule hash.
3. PR 5 creates blind-judge and human-audit attachments that reference the same hash.
4. PR 6 assembles a publication bundle from those immutable layers.

This avoids a mutable monolithic result directory. Adding a judgment or recomputing an analysis
never changes the provider requests, input snapshots, schedule, attempt history, or capsule hash.

## 2. Objective

The current runner already validates schemas, records retry histories, redacts known secrets,
recovers a single uncommitted JSONL tail, and rejects mismatched provenance. Its CLI still reads
cases, arms, and replay data from the current checkout, creates a new directory for every `run`,
and has no public `plan`, `resume`, or `verify` command.

PR 3 must ensure that:

- every input is captured before the first provider call;
- the exact request schedule is materialized before execution;
- execution and resume use only captured inputs;
- every possible paid request has a write-ahead identity;
- concurrent mutators cannot duplicate calls;
- a copied or renamed capsule can be verified without its source checkout;
- structural verification is possible with a newer compatible verifier;
- a completed or blocked generation history can be sealed and referenced immutably.

PR 3 makes no model-performance claim and makes no live provider call in tests.

## 3. Approaches considered

### A. Compatibility shim

Copy cases and arms next to the current `manifest.json`, `raw.jsonl`, and `run.log`, while retaining
the current command flow. This is smaller, but keeps ambiguous path ownership, directory-name run
identity, post-provider directory creation, and weak crash/concurrency semantics.

### B. Capsule-first generation lifecycle — selected

Create a complete generation capsule in a staging directory, publish it before provider
construction, execute against the materialized plan, and seal it after generation completes or
is deliberately abandoned. This establishes one durable source of truth for every later layer.

### C. One-shot publication archive

Build a complete archive only after generation, scoring, judging, and reporting. This produces a
simple final download but does not solve resume, invisible duplicate calls, input drift, or
crash-safe ownership during the run.

## 4. PR boundary

PR 3 includes:

- capsule schema v1, attempt schema v2, and event schema v1;
- exact case, arm, replay, protocol-binding, and software-provenance snapshots;
- a materialized execution plan and stable scenario/case/request identities;
- atomic capsule preparation;
- `plan`, capsule-backed `run`, `resume`, `verify`, and `finalize` commands;
- an append-only lifecycle/request journal;
- write-ahead request records and explicit ambiguous in-flight handling;
- exclusive mutator and shared verifier locking on local POSIX filesystems;
- one-file atomic sealing for complete and intentionally abandoned generation capsules;
- stable capsule, protocol, plan, attempt, and response identities for later attachments.

PR 3 explicitly excludes:

- confidence intervals, bootstrap mechanics, power analysis, margins, or outcome thresholds;
- `supported`, `rejected`, savings, superiority, or publication-readiness decisions;
- capsule-native scoring and reporting attachments;
- judge request generation, live judging, human sampling, preference ratings, or adjudication;
- corpus expansion, a paid benchmark campaign, GitHub administration, a tag, or a release;
- automatic continuation after a provider-returned authentication failure;
- signatures or external proof that an author did not replace a capsule and its seal.

The existing standalone `score` and `report` commands remain available for smoke workflows during
PR 3 through the explicit compatibility projection in section 18. V1 still requires explicitly
supplied case files; v2 uses only captured capsule cases. Both remain non-publication mechanics. This keeps the documented
`run -> score -> report` smoke path working while PR 4 designs capsule-bound scoring and inference
attachments.

## 5. Trust boundary

Application code owns input capture, path resolution, identifiers, schedule construction,
locking, provider calls, retries, redaction, append/fsync behavior, verification, and sealing.
Provider responses, case text, arm instructions, error messages, judgments, and future attachment
payloads are untrusted data. None may select files, alter destinations, change a retry policy, or
advance lifecycle state directly.

Generated metadata, events, and diagnostics never deliberately store an API-key value, environment
dump, hostname, username, a host path known to the harness (capsule root, source root, invocation
working directory, or home directory), private-index URL, Git diff, arbitrary Git remote, or
unrestricted `pip freeze`. Only the allowlisted provenance fields in section 13 are generated.
Exact authored manifest values, case, arm, replay, protocol, runner-source, and retained
provider-output bytes are opaque evidence and can themselves contain sensitive text supplied by an
author or provider; a generation capsule is therefore private-by-default and not publication-ready.
PR 6 performs a fail-closed secret scan before publication. Known credential values are still
redacted from outputs/diagnostics and are never intentionally copied as API configuration.

### Resource bounds

`ResourceLimitsV1` is a package constant recorded by version in `capsule.json` and enforced before
allocation, parsing, planning, or the next provider call:

| Resource | Limit |
|---|---:|
| source manifest | 1 MiB |
| one/all case files | 8 MiB / 64 MiB |
| one/all arm members | 2 MiB / 8 MiB |
| replay fixture | 256 MiB |
| one/all protocol files | 16 MiB / 64 MiB |
| one/all runner-source files | 2 MiB / 32 MiB |
| one/all retained dependency files | 64 MiB / 512 MiB |
| dependency distributions / files / requirements | 1,000 / 100,000 / 100,000 |
| dependency marker contexts / requirement evaluations | 100,000 / 100,000 |
| captured input total | 512 MiB |
| case records / plan rows / raw rows | 10,000 / 100,000 / 600,000 |
| plan or event JSONL row | 1 MiB |
| raw JSONL row / output UTF-8 | 16 MiB / 2 MiB |
| output-token limit per request / across materialized plan | 65,536 / 10,000,000 |
| complete mutable capsule before seal | 8 GiB |
| diagnostic message | 4 KiB |
| model, request, finish, schema, binding, and locator string | 1 KiB |
| YAML/JSON nesting depth | 64 |

MiB/GiB are binary units. YAML anchors, aliases, and merge keys are rejected; collection counts are
checked before model construction. Limits apply to encoded UTF-8 bytes, not characters. Before an
execution epoch reads credentials or constructs a provider, and again before each
`request_started`, the runner verifies that the logical capsule limit has room for the complete
worst-case attempt transaction: request-start event and LF, maximum raw row and LF, request-finish
event and LF, the required stop/ambiguity/completion-or-interruption event and LF, plus one later
seal-request event and LF. Already reserved bytes are not double-counted. Insufficient capacity
stops before the call; the epoch-level check additionally covers `execution_started` and a possible
`execution_blocked` event. A single maximum legal row is not an adequate reservation. An
oversized post-secret-redaction output is never written: its byte length and SHA-256 are recorded in a terminal
`response_too_large` provider-rejected attempt with `delivery_certainty=response_received`.
Resource-limit errors contain no rejected bytes.

## 6. Directory contract

A prepared capsule has this exact owned layout:

```text
<run-dir>/
├── capsule.json
├── manifest.json
├── environment.json
├── case-index.jsonl
├── plan.jsonl
├── events.jsonl
├── raw.jsonl
├── inputs/
│   ├── index.json
│   ├── cases/
│   │   ├── 000.yaml
│   │   └── ...
│   ├── arms/
│   │   ├── baseline.txt
│   │   ├── concise.txt
│   │   ├── caveman/
│   │   │   ├── SKILL.md
│   │   │   ├── SOURCE.md
│   │   │   └── LICENSE.txt
│   │   └── if/
│   │       └── SKILL.md
│   ├── provider/
│   │   └── replay.yaml
│   ├── protocols/
│   │   └── <three-digit-ordinal>-<binding-id-sha-prefix>.bin
│   └── software/
│       ├── runner/
│       │   └── laconian_eval/
│       │       └── ...
│       └── runner-source.json
└── .laconian.lock
```

`inputs/provider/replay.yaml` exists only for a replay manifest. `inputs/protocols/` contains only
bindings declared before preparation. Arms not selected by the manifest are not copied.
Protocol destination names are `<ordinal:03d>-<first-16-hex-of-SHA256(UTF8(binding_id))>.bin`;
untrusted kind, media type, source suffix, and binding text never become path components.
`baseline.txt` is exactly zero bytes, so its `instruction_sha256` is SHA-256 of empty bytes;
`concise.txt` contains exact UTF-8 `Answer concisely.` with no added newline. File-backed arm hashes
cover their exact captured UTF-8 instruction bytes.

Request reconstruction preserves the semantic sentinel: baseline sends `instructions=null`, never
an empty string; concise sends the exact `concise.txt` text; `if` and Caveman send only their exact
captured `SKILL.md` text. Caveman `SOURCE.md`/license files are provenance-only and never enter the
request instruction slot.
For v0.1, Caveman capture rejects anything except commit
`781c384cafc28d7ca392014dbab569f985b5b2fd`, exact `SKILL.md` SHA-256
`1eddf7055618153869975678d9ff36635602a3aa333f8b4cc0787f12de75b6f8`, and the bundled MIT license;
the copied provenance files and input index make that pin independently visible.

A sealed capsule additionally contains one atomically published file:

```text
seal.json
```

`.laconian.lock` is mandatory for every local mutable capsule. Because it is operational state and
excluded from the seal, an offline transport copy of an already sealed capsule may omit it; such a
copy is verifiable but no command may make it mutable again.

PR 3 does not create empty `judgments/`, `scored/`, or report placeholders. Future attachments are
separate immutable directories and therefore do not change the generation-capsule root hash.

All owned files are regular files. Symlinks, devices, sockets, path traversal, and normalized-path
collisions are rejected. Detectable descriptor metadata changes during capture are rejected; the
exact single-read bytes and their digest remain the source of truth because a local filesystem
cannot prove the absence of every concurrent in-place write. The run directory is created with
mode `0700`; owned files are created with mode `0600`, subject to a stricter umask.

## 7. Source capture and path semantics

Source-manifest v1 retains the current read compatibility: relative `case_files` and
`provider.replay_file` values resolve against the invocation working directory, and an explicitly
declared absolute v1 path may be read. Every relative v2 case, replay, and protocol path resolves
descriptor-relative beneath `--input-root`, whose default is the directory containing the source
manifest; it is independent of the invocation working directory and `--source-root`. The input root
is a verified non-symlink directory used only during preparation and is never serialized. This lets
repository manifests name `evals/cases/...` and `tests/fixtures/...` under an explicit project-root
input root without permitting `..`. Source-manifest v2 accepts only normalized relative paths;
absolute paths, traversal, empty components, and platform-prefix aliases are rejected.
Passing `--input-root` with source-manifest v1 is a usage error rather than a silent change to its
CWD-compatible resolution semantics.
Resolution occurs only while preparing the capsule, and no literal source path is serialized:
input provenance uses logical locators such as `case_files[0]`, `provider.replay_file`,
`capsule.protocol_bindings[2].path`, `arm[if]/SKILL.md`, or
`package[laconian_eval]/providers/openai.py`.

For each source, preparation opens without following symlinks, compares descriptor metadata
before and after one bounded regular-file read, then validates and hashes the captured bytes. It
never validates one read and copies a second read. Case destinations use manifest ordinal names
(`000.yaml`, `001.yaml`) rather than basenames, preventing collisions.

`manifest.json` is canonical validated JSON with case, replay, and protocol paths rewritten to
capsule-relative snapshot paths. It contains no resolved host path. `capsule.json` records both:

- `source_manifest_commitment_sha256`, computed from the exact source YAML bytes;
- `manifest_sha256`, computed from the canonical resolved manifest.

The exact source manifest is not copied because YAML comments may contain secrets or local paths;
its semantic content is completely represented by `manifest.json`, and its original bytes remain
bound externally by `source_manifest_commitment_sha256`. Because the source bytes are intentionally
not copied, the verifier reports this value as a producer commitment rather than a self-contained
hash it can recompute.

After publication, `resume`, `verify`, and every future attachment command resolve files only
through `inputs/index.json`. They do not inspect the original manifest location, source checkout,
working directory, Git tree, or global arm paths.

The API-key environment-variable name remains in the canonical manifest. Its value never does.

## 8. Capsule identity and predeclared intent

`capsule.json` is immutable after preparation and uses a schema independent of `RunManifest`:

```yaml
capsule_schema_version: "1"
attempt_schema_version: "2"
event_schema_version: "1"
resolved_manifest_schema_version: "2"
resource_limits_version: "1"
canonicalization_version: laconian-json-v1
sanitizer_version: laconian-sanitizer-v1
runner_version: <current package version>
run_id: <uuid>
created_at: <UTC RFC 3339>
run_purpose: integration_smoke | development | confirmatory_author_run | replication
claim_intent: none | exploratory | confirmatory_candidate
schedule_algorithm_version: laconian-schedule-v1
arm_order_seed: <integer>
source_manifest_commitment_sha256: <sha256>
manifest_sha256: <sha256>
input_index_sha256: <sha256>
case_index_sha256: <sha256>
plan_sha256: <sha256>
environment_sha256: <sha256>
runner_source_sha256: <sha256>
```

The model is strict: all displayed fields are required, hashes are lowercase 64-hex, and no unknown
field is accepted. `run_id` is UUIDv4 stored in the capsule and every attempt; `created_at` uses the
one canonical timestamp spelling in section 9. Runner version equals the resolved manifest,
environment package version, session package version, and every raw row. Purpose, claim intent,
schedule version/seed, and manifest hash must equal the resolved manifest. The ID is not derived
from the directory basename, so copying or renaming a capsule does not alter identity.

`SourceManifestV2` is strict and has this complete top-level shape:

```yaml
schema_version: "2"
runner_version: <current package version>
run_name: <[a-z0-9][a-z0-9-]+>
provider:
  kind: fake | replay | openai
  model: <nonblank string>
  api_key_env: <[A-Z_][A-Z0-9_]{0,127} or null>
  replay_file: <path or null>
case_files: [<one or more paths>]
arms: [<one or more unique baseline | concise | caveman | if>]
repetitions: <integer 1..100>
arm_order_seed: <signed 64-bit integer>
instruction_placement: system_suffix
generation:
  max_output_tokens: <integer 1..65,536>
  temperature: <finite number 0..2 or null>
retry:
  max_transient_retries: <integer 0..5>
  timeout_seconds: <finite number > 0 and <= 600>
price_snapshot:
  currency: USD
  effective_date: <YYYY-MM-DD>
  source_url: <absolute ASCII HTTP(S) URL>
  input_per_million: <finite number >= 0>
  cached_input_per_million: <finite number >= 0 or null>
  output_per_million: <finite number >= 0>
  # or the entire price_snapshot value is null
capsule:
  run_purpose: integration_smoke | development | confirmatory_author_run | replication
  claim_intent: none | exploratory | confirmatory_candidate
  datasets:
    - dataset_id: <nonblank stable string>
      dataset_version: <nonblank stable string>
      role: smoke | development | calibration | held_out_test | challenge
      case_schema_version: "1"
      case_file_ordinals: [<zero-based source-manifest ordinals>]
  comparisons:
    - comparison_id: <nonblank stable string>
      left_arm: baseline | concise | caveman | if
      right_arm: baseline | concise | caveman | if
      role: primary | secondary | contextual | diagnostic
  protocol_bindings:
    - binding_id: <nonblank stable string>
      kind: <nonblank namespaced string>
      schema_id: <nonblank namespaced string>
      media_type: <nonblank media type>
      path: <relative source path>
      scope:
        dataset_ids: [<declared IDs>]
        comparison_ids: [<declared IDs>]
      bound_at_stage: pre_generation
      applies_at: [scoring | judging | inference | publication, ...]
      declared_requirement: optional | required_for_declared_claim
```

Provider cross-rules are exact: OpenAI requires `api_key_env` and forbids `replay_file`; replay
requires `replay_file` and forbids `api_key_env`; fake forbids both. All integers are strict
non-boolean values. `price_snapshot`, when present, is the current strict v1 object: USD currency,
effective date, absolute ASCII HTTP(S) source URL, nonnegative finite input/output per-million
prices, and nullable nonnegative finite cached-input price. The URL scalar rejects leading or
trailing whitespace, controls, user information, and fragments; after validation its exact source
string is retained rather than normalized. Defaults are the existing v1 defaults before canonical
serialization. Capsule preparation applies the same exact-string URL projection, bounded
environment-variable grammar, signed-64-bit seed range, per-request output-token bound, and
materialized-plan token-exposure limit to a v1 manifest before resolving it.

`datasets` is nonempty; `comparisons` and `protocol_bindings` may be empty. Every dataset owns at
least one case file. Dataset IDs, comparison IDs, and binding IDs are individually unique. Every
case-file ordinal is in range and belongs to exactly one dataset. Both comparison arms are selected
and distinct; an unordered pair appears once; at most one comparison is primary. Each protocol
scope names at least one dataset or comparison and references only declared IDs. PR 3 snapshots and
binds protocol bytes but does not interpret their research constants or decide whether a declared
claim is supported. `bound_at_stage` is the literal `pre_generation`; `applies_at` is a nonempty,
duplicate-free list in the fixed enum order shown above. Later evidence refers to the pair
`(capsule_sha256, binding_id)`.

After case loading, locale cardinality and uniqueness are revalidated by
`(dataset_id, scenario_id)`. All localized records of one source scenario must be assigned to the
same dataset; splitting its English/Russian pair across dataset bindings is invalid. Reusing a
human-readable scenario ID in another dataset is permitted only when that dataset independently
contains its complete locale set.

The canonical `manifest.json` is `ResolvedManifestV2` with `schema_version: "2"` and
`source_manifest_schema_version: "1" | "2"`. It contains the same validated logical values,
rewrites case/replay/protocol paths to capsule-relative paths, and adds each dataset's
`dataset_content_sha256` plus each protocol binding's byte length and SHA-256. These are its only
shape differences from the complete model above:

- `source_manifest_schema_version` is added beside `schema_version`;
- fixed `schedule_algorithm_version: laconian-schedule-v1` is added;
- `case_files`, replay path, and protocol `path` contain normalized capsule paths;
- each dataset adds required `dataset_content_sha256`;
- each protocol adds required `byte_length` and `sha256`;
- the provider cross-rules, ranges, defaults, ordering, and capsule declarations are unchanged.

It never contains a host-absolute path. `SourceManifestV1` remains the current strict `RunManifest`; no v2 field is
silently added to that model. Preparation upgrades v1 in memory using exactly these defaults:

- `run_purpose=integration_smoke`, `claim_intent=none`;
- one dataset whose ID is `run_name`, version is the literal `unversioned`, role is `smoke`, and
  whose ordinals cover every case file in source order;
- one `if-vs-concise` contextual comparison only when both arms are selected;
- no protocol bindings;
- provider fields ignored by the selected v1 kind are normalized to null: OpenAI drops
  `replay_file`, replay drops `api_key_env`, and fake drops both. The source-byte commitment still
  binds what the author supplied.

`inputs/index.json` is strict `InputIndexV1`:

```yaml
schema_version: "1"
manifest_sha256: <resolved-manifest sha256>
files:
  - role: case | arm | replay | protocol | runner_source
    role_ordinal: <zero-based integer>
    logical_locator: <stable field/package locator>
    capsule_path: <normalized relative POSIX path>
    byte_length: <nonnegative integer>
    sha256: <sha256>
    dataset_id: <ID or null>
    binding_id: <ID or null>
```

File records are sorted by UTF-8 `capsule_path`, and paths are unique. For cases, `role_ordinal` is
the source-manifest case-file ordinal; for protocols, the declared binding ordinal; for selected
arms, the manifest arm ordinal (shared by that arm's multiple files); for replay, zero; and for
runner source, its sorted inventory ordinal. `dataset_id` is nonnull only for cases, `binding_id` is
nonnull only for protocols, and both are null for other roles. `logical_locator` is one of the
bounded forms in section 7 and never contains the literal or resolved source path. The index covers
every immutable input and runner-source file exactly once; generated
metadata, ledgers, the persistent lock, and the seal are not input-index members.

No PR 3 field fixes a sample size, repetition count beyond the operational manifest value,
non-inferiority margin, confidence level, bootstrap draw count, coverage threshold, or rater
count. Those belong to later bound protocols and attachments.

## 9. Stable case and plan identities

Every PR 3 generated JSON document, JSONL row, and structured digest uses the same normative
encoding. `canonical_json(value)` is the UTF-8 result of
`json.dumps(value, sort_keys=True, separators=(",", ":"), ensure_ascii=False,
allow_nan=False)`, with no trailing newline. Before serialization, datetimes are UTC strings in
`YYYY-MM-DDTHH:MM:SS.ffffffZ`, dates are `YYYY-MM-DD`, UUIDs are lowercase hyphenated strings,
enums are their string values, and paths are normalized relative POSIX strings. Every declared
floating-point field is converted to a finite Python `float`, including a YAML integer spelling,
and negative zero is normalized to positive `0.0`; JSON spelling is then determined by the exact
`json.dumps` call above. A validated price-source URL retains the exact accepted ASCII source
string defined in section 8. Strings are otherwise hashed as supplied; there is no Unicode
normalization. `stable_digest(domain, payload)` is lowercase hexadecimal
`SHA256(UTF8(domain) || 0x00 || canonical_json(payload))`; `stable_digest_bytes` is the same
operation's raw 32 bytes. Integers are JSON integers, missing optional values are JSON `null`,
ordinals and repetition indexes are zero-based, and no implementation-language object
representation is part of a preimage. Canonical JSONL is one such object plus one LF byte per row;
file hashes cover those exact bytes including every LF.

Generated run, operation, execution-session, and seal-transaction identifiers are independent
UUIDv4 values. User-declared IDs are bounded strings and are never parsed as paths.

Generated single-object JSON files are exactly `canonical_json(object)` with no LF. Their named
`*_sha256` fields in `capsule.json` are plain lowercase SHA-256 of those complete bytes; JSONL file
hashes are plain SHA-256 of the complete LF-framed file. Captured YAML/text/source hashes cover
their exact captured bytes and do not use JSON canonicalization. `raw_record_sha256` is derived
from an already validated canonical row without its LF and is never embedded in that raw row.
Implementation tests include fixed golden byte strings and digests for every schema and identity.

`case-index.jsonl` contains one canonical-JSON record per localized response case:

```text
dataset_id
dataset_version
dataset_role
source_ordinal
record_ordinal
case_id
case_uid
scenario_id
scenario_uid
locale
category
case_definition_sha256
prompt_sha256
```

The model is strict. Ordinals are nonnegative integers; IDs retain the current response-case
patterns; locale is `en|ru`; category is one of `direct`, `coding`, `preservation`,
`structured-output`, `uncertainty`, `safety`, `user-message`, or `summarization`; and every digest
is lowercase 64-hex. Case IDs and case UIDs are globally unique, scenario UIDs obey the
dataset-scoped locale rule, and no unknown field is accepted.

`case_definition_sha256` is the existing canonical `ResponseCase` digest; `prompt_sha256` is
SHA-256 of exact UTF-8 prompt bytes. The remaining case identities are:

```text
dataset_content_sha256 = stable_digest("laconian-dataset-content-v1", {
  "dataset_id": dataset_id,
  "dataset_version": dataset_version,
  "members": [{
    "source_ordinal": source_ordinal,
    "capsule_path": capsule_path,
    "byte_length": byte_length,
    "sha256": sha256
  }, ...]
})
scenario_uid = stable_digest("laconian-scenario-v1", {
  "dataset_id": dataset_id,
  "dataset_version": dataset_version,
  "scenario_id": scenario_id
})
case_uid = stable_digest("laconian-case-v1", {
  "scenario_uid": scenario_uid,
  "case_id": case_id,
  "locale": locale,
  "case_definition_sha256": case_definition_sha256
})
```

Dataset members remain in source-manifest ordinal order. Case-index order is source case-file
ordinal ascending, then record ordinal ascending. `plan.jsonl` is the execution source of truth and
is materialized before provider construction. Plan blocks follow case-index order, then repetition
ascending from zero. Within each case/repetition block, arms are sorted by `stable_digest_bytes`
from:

```text
stable_digest("laconian-schedule-v1", {
  "seed": arm_order_seed,
  "case_uid": case_uid,
  "repetition": repetition,
  "arm": arm
})
```

with arm ID as the impossible-collision tie-breaker. This deliberately replaces dependence on
Python's `random.Random`. `capsule.json` records `schedule_algorithm_version=laconian-schedule-v1`
and the seed; both producer and verifier implement that exact permutation.

Each canonical plan row contains:

```text
ordinal
plan_item_id
pairing_unit_id
case_uid
scenario_uid
case_id
locale
repetition
arm
block_id
arm_position
prompt_sha256
case_definition_sha256
instruction_sha256
request_config_sha256
```

The plan-row model is strict: ordinals, repetition, and arm position are nonnegative integers; arm,
case ID, locale, and all digests must match the referenced strict case/manifest records; unknown
fields are rejected.

The exact plan preimages are:

```text
block_id = stable_digest("laconian-block-v1", {
  "run_id": run_id,
  "case_uid": case_uid,
  "repetition": repetition
})
pairing_unit_id = stable_digest("laconian-pairing-unit-v1", {
  "run_id": run_id,
  "case_uid": case_uid,
  "repetition": repetition
})
request_config_sha256 = stable_digest("laconian-request-config-v1", {
  "provider_kind": provider_kind,
  "requested_model": requested_model,
  "generation": {
    "max_output_tokens": max_output_tokens,
    "temperature": temperature
  },
  "retry": {
    "max_transient_retries": max_transient_retries,
    "timeout_seconds": timeout_seconds
  },
  "instruction_placement": instruction_placement,
  "store": false,
  "tools": []
})
plan_item_id = stable_digest("laconian-plan-item-v1", {
  "run_id": run_id,
  "case_uid": case_uid,
  "repetition": repetition,
  "arm": arm,
  "instruction_sha256": instruction_sha256,
  "request_config_sha256": request_config_sha256
})
```

The generation and timeout values are the canonical resolved-manifest JSON values. No secret or
environment value enters a digest. Verification requires exactly one plan row for every captured
case × manifest repetition × selected arm combination, consecutive unique ordinals, unique IDs,
and arm positions `0..arms-1` inside every block. Retries are attempt records, never plan rows.

The remaining runtime identities are normative here so later attachments need not reinterpret
them:


All SHA-256 results are lowercase hexadecimal. `response_id` exists only for a successful terminal

## 10. Lifecycle and derived state

There is no authoritative mutable `state.json`. State is derived from the exclusive lock,
append-only events, plan, raw ledger, and optional seal artifacts.

The observable generation states are:

```text
CREATING                 hidden staging directory, not a capsule
PREPARED                 published inputs and plan; no active execution
RUNNING                  an execution session holds the exclusive lock
INTERRUPTED              incomplete plan, no active lock, safely resumable
AMBIGUOUS_INFLIGHT       an unresolved request may have reached the provider
AUTHENTICATION_STOPPED   provider returned a terminal authentication error
GENERATION_COMPLETE      every plan item has one resolved non-auth terminal outcome
SEALING_INTERRUPTED      one seal request exists but seal publication did not finish
SEALED_COMPLETE          complete capsule with valid atomic seal
SEALED_BLOCKED           incomplete capsule deliberately sealed with blockers
INVALID                  structural or cryptographic verification failure
```

Allowed transitions are:

```text
CREATING -> PREPARED
PREPARED -> RUNNING
RUNNING -> PREPARED (only a closed no-call blocked epoch) | INTERRUPTED | AMBIGUOUS_INFLIGHT |
           AUTHENTICATION_STOPPED | GENERATION_COMPLETE
INTERRUPTED -> RUNNING
PREPARED | INTERRUPTED | AMBIGUOUS_INFLIGHT |
AUTHENTICATION_STOPPED | GENERATION_COMPLETE -> SEALING_INTERRUPTED
SEALING_INTERRUPTED -> SEALED_COMPLETE | SEALED_BLOCKED
```

`RUNNING` exists only while the process holds the kernel lock. A stale textual status cannot make
a run appear active. `INVALID` is a verifier classification and is never written as an attempt to
repair or legitimize corrupt bytes. `SEALING_INTERRUPTED` is not resumable generation; only an
idempotent `finalize` may complete the already-requested seal.

Missing credentials or provider-construction failure leaves a capsule `PREPARED` only while its
request history is empty; after any prior request history the same closed no-call epoch leaves it
`INTERRUPTED`. Either may be resumed, or sealed blocked; only the former uses `never_started` plus
the bounded operational reason code.
A provider-returned authentication error is recorded, stops before later plan items, and is not
resumed in PR 3. Corrected credentials start a new run; the old capsule may be sealed blocked.
Ordinary non-retryable provider errors remain terminal outcomes for their plan item and execution
continues.

Generation completion counts `success`, `retry_exhausted`, and `provider_rejected` as resolved
terminal outcomes. `authentication_stopped` keeps the capsule incomplete even on the last plan
item; `ambiguous_delivery` is terminal for retry lineage but unresolved for plan coverage and is
included with all later uncalled items in `missing_plan_item_ids`.

Successful attempts may expose more than one nonblank provider-returned model identifier. This is
structurally valid generation evidence: execution continues, the exact sorted set is disclosed in
the seal, and later analysis decides whether the run is comparable. A provider that is required by
its adapter contract to return a model identifier but omits or malforms it produces an invalid
adapter result before a success row is committed; mixed valid identifiers are never corruption.

A crash after the last raw result but before a completion event is recovered without a provider
call: `resume` verifies complete plan coverage and appends a recovery completion event.

For a quiescent capsule, state is derived in this precedence order:

1. any schema/hash/history contradiction is `INVALID`;
2. a valid `seal.json` is `SEALED_COMPLETE` or `SEALED_BLOCKED` from its validated contents;
3. exactly one valid `seal_requested` without a seal is `SEALING_INTERRUPTED`;
4. an unmatched request start or `ambiguous_delivery` row is `AMBIGUOUS_INFLIGHT`;
5. an authentication terminal row is `AUTHENTICATION_STOPPED`, even if its marker is missing;
6. resolved terminal coverage of the complete plan is `GENERATION_COMPLETE`, even if its marker is
   missing;
7. a capsule with zero request history whose latest no-call session closed by `execution_blocked`
   is `PREPARED`;
8. any request history or other execution history with incomplete coverage is `INTERRUPTED`;
9. a published capsule with only preparation history is `PREPARED`.

While an exclusive lock is held, cooperative observers return `busy` rather than applying this
quiescent classifier. Missing authentication, ambiguity, or completion marker events are recovered
from already committed raw/finish records without a provider call; the derived safety state never
depends on the marker being present.

## 11. Write-ahead events and raw attempt schema

`events.jsonl` is append-only and fsynced per canonical-JSON line. Every event has
`schema_version: "1"`, consecutive `sequence`, `event_id`, `run_id`, UTC timestamp, `kind`, a
required UUID `operation_id`, a nullable UUID `execution_session_id`, and a strict kind-specific
payload. `operation_id` identifies one CLI invocation even when provider construction never starts;
`execution_session_id` identifies a lock-held provider execution and is null for preparation,
verification-independent recovery planning, and sealing.

Sequence starts at zero. The common serialized keys are exactly `schema_version`, `sequence`,
`event_id`, `run_id`, `occurred_at`, `kind`, `operation_id`, `execution_session_id`, and `payload`.
The schema version is literal `"1"`; sequence is a nonnegative integer; event ID is SHA-256; run,
operation, and nonnull session IDs are UUIDs; occurrence time is canonical UTC; and kind is exactly
one discriminator listed below. No common or payload key is optional unless its type explicitly says
null.

It contains no Git, path, or credential field. Fake/replay require both SDK fields null; OpenAI
requires `sdk_distribution=openai` and a nonnull version. A normal
`request_finished` has `recovered=false` and the same operation/session as its referenced start; a
recovered finish has `recovered=true`, the current recovery operation, a null session, and retains
the exact origin `request_started_event_id`. Nullable
payload fields use explicit JSON null and unknown payload keys are rejected. `execution_started`,
`execution_blocked`, `request_started`, a normal `request_finished`, `execution_interrupted`, and a
normal `generation_completed` require a nonnull execution-session ID. Authentication/ambiguity
markers require it when `recovered=false`. A recovered finish/stop/ambiguity marker has the current
recovery operation, `recovered=true`, the origin start-event ID, and null session. A normal
completion has `recovered=false`, references the final `request_finished` event, and uses that
event's operation/session; a recovered completion has `recovered=true`, the current recovery
operation, the exact final `request_finished` event ID, and null session. `prepared`,
`tail_recovered`, and `seal_requested` also require null session.
Normal stop/ambiguity markers have `recovered=false` and the origin start's operation/session.

Every valid history starts with exactly one `prepared` event at sequence zero. Later events form
ordered execution epochs and recovery operations. An execution epoch starts with exactly one
`execution_started`; its nonnull-session events share that event's operation/session. It either
ends with `execution_blocked`, `execution_interrupted`, a normal stop/ambiguity/completion marker,
or is implicitly crash-ended before the next epoch. A new epoch is invalid while a request start is
open. Each request start is followed by at most one matching raw row and finish before another
request start; the reconciliation table in section 12 defines the only recoverable absences.
Recovery events use their current invocation operation ID and null session. `seal_requested` is the
single final event. Authentication/ambiguity/completion markers may be absent only when their exact
meaning is already derivable from committed start/raw/finish records after a crash; when present,
their identities and ordering must match those records. An unmatched start with no raw row is
markerless ambiguity, not a fabricated `delivery_ambiguous` result.
`tail_recovered.related_attempt_id` is nonnull exactly when a removed raw tail corresponds to the
one durable open request start; it equals that start's attempt ID and is null for every other tail.
`tail_recovered.removed_byte_count` is the exact byte length of the one unterminated suffix removed
after the final LF, and `removed_sha256` is SHA-256 of those exact removed bytes. It never hashes a
decoded, normalized, or reserialized value.

`execution_started.resume_from_plan_ordinal` is exactly the ordinal of the first materialized plan
item without a resolved terminal outcome at the start of that epoch. If that item already has a
valid safe-retry history, the ordinal does not advance and the next request continues that same
retry lineage. No `execution_started` is written when only a finish/marker/completion recovery
remains. `execution_interrupted.next_plan_item_id` is exactly that same first unresolved item after
the epoch's last committed finish; the event is legal only with no open request and a history that
is safely resumable. An open request or unknown-delivery row derives ambiguity instead and cannot
be labeled interruption.

Every `request_started` must target that current first unresolved plan ordinal. It may repeat the
same plan item only as the next consecutive attempt in its immediate safe-retry lineage; otherwise
it is attempt one. No later plan item may start until the current one has a resolved terminal
outcome, so any skip or reordering is invalid. `generation_completed.terminal_plan_item_count` is
exactly the materialized plan cardinality, `final_plan_ordinal` is exactly cardinality minus one,
and `origin_request_finished_event_id` is the finish that binds the resolved terminal row for that
last ordinal.

No event is appended after `seal.json` is published. All reason codes are enums; exception text is
redacted diagnostic data and never participates in lifecycle derivation.

After immutable/resume validation and before credential access, a resume that can start provider
execution commits `execution_started`. A marker/finish/completion-only recovery operation is the
explicit exception: it uses null-session recovery events and never creates an execution epoch.
Credential or provider-construction failure commits `execution_blocked` and
releases the lock without a request start. Provider construction itself is not a provider request;
no generation call is possible before the write-ahead step below.

Before every provider call, the runner appends and fsyncs `request_started` containing:

- `plan_item_id`, deterministic `attempt_id`, attempt number, and retry parent;
- request-config, prompt, case-definition, and instruction hashes;
- requested provider and model;
- no prompt text, instruction text, API key, or arbitrary provider payload.

After the provider returns, the runner appends and fsyncs the raw attempt, then appends and fsyncs
`request_finished`. A raw row without the final event is recoverable from the raw identity without
another provider call.

An unmatched `request_started` is `AMBIGUOUS_INFLIGHT`: the process may have paid for a request
whose result was not durably recorded. PR 3 never retries it automatically and never fabricates a
favorable or unfavorable provider result. The operator may inspect or seal the capsule blocked;
a fresh run is required for a complete experiment. Later provider-specific idempotency support
requires its own design.

A returned error is not automatically safe to retry. Each adapter supplies `delivery_certainty`:

- `definitely_not_sent`: local transport proof that no request bytes were sent;
- `definitely_rejected`: an explicit provider response proving that generation was rejected;
- `response_received`: a success or malformed/terminal response was received;
- `unknown`: the request may have been accepted or billed but no usable response proves its fate.

`error.retryable` describes transience only. The runner retries solely when it is true *and*
certainty is `definitely_not_sent` or `definitely_rejected` and budget remains. A non-authentication `unknown` commits a
terminal attempt with `terminal_reason=ambiguous_delivery`, appends `delivery_ambiguous`, leaves the
plan item unresolved for generation-completion purposes, stops every later call, and derives
`AMBIGUOUS_INFLIGHT`. OpenAI connection errors, timeouts, HTTP 408, and 5xx are `unknown` unless the
SDK supplies narrower proof; explicit rejected 4xx/API error responses such as validation,
authentication, conflict, and rate-limit rejection are `definitely_rejected`; a parsed response is
`response_received`. Tests cover post-send timeout and 5xx paths. Provider-specific idempotency is
future work.

`response_id` is an opaque digest over run, plan, attempt, case, instruction, and output identity.
It is the stable response target for future semantic judgment; other future evidence may need a
plan, attempt, pair, or dependency target as described in section 17. Raw rows remain
judgment-free. Every provider call remains represented, including retryable errors, exhausted
retries, non-retryable errors, and successful calls.

Every persisted string must encode with strict UTF-8; unpaired surrogates are never canonicalized.
Invalid provider output becomes a `malformed_response` provider-rejected row with
`response_received`; an invalid diagnostic is replaced by a constant safe diagnostic, and invalid
non-output identity metadata follows the `unsafe_provider_metadata` rule below.

Usage semantics are exact. `unavailable` requires all four token counts null. `partial` requires at
least one but not all of input/output/total; `complete` requires input/output/total and requires
`total_tokens = input_tokens + output_tokens`. Counts are nonnegative. Cached input may be null
even with otherwise complete core usage only when `cache_accounting=not_reported`; zero is a
reported zero and is never converted to null. `reported` requires a nonnull cached count;
`not_reported` and `not_applicable` require null. All counts are strict non-boolean integers.
A nonnull cached count requires a nonnull input count and must satisfy
`0 <= cached_input_tokens <= input_tokens`. `source=provider` means values were
reported directly; `source=adapter` means the adapter deterministically derived them. Either source
may be complete/partial/unavailable, but it may not convert absence into zero. Error attempts may
contain usage.

The attempt-state truth table is:

| State | `terminal` | Output/error | Delivery | Terminal reason |
|---|---:|---|---|---|
| success | true | nonblank output, no error | `response_received` | `success` |
| safe retry | false | retryable non-auth error | not-sent/rejected | null |
| exhausted | true | retryable non-auth error at budget | not-sent/rejected | `retry_exhausted` |
| rejected | true | any remaining non-auth error | any non-unknown value | `provider_rejected` |
| authentication | true | normalized auth error | rejected/response | `authentication_stopped` |
| ambiguous | true | error, no usable output | `unknown` | `ambiguous_delivery` |

An auth-shaped adapter result is accepted as authentication only with
`definitely_rejected` or `response_received`. Any auth-shaped `unknown` or `definitely_not_sent`
combination is contradictory adapter evidence and is normalized to an `unknown`
`ambiguous_auth_delivery` error before persistence. Classification precedence is therefore unknown
delivery, then valid authentication, then safe retry when transient plus safe delivery plus
remaining budget, then retry exhaustion when that same safe transient error reaches budget, then
`provider_rejected` for every other error regardless of its transience flag.
Only safe retry has nonnull `backoff_ms`. Success alone has output/response identity. Every error
state requires `error` and has null output/output hash/response identity. Authentication and
ambiguous delivery require their matching marker in a normalized history; a crash-missing marker is
a valid recoverable absence only while its exact identity is derivable from the committed
start/raw/finish chain. `resume` or `finalize` appends it without a provider call before advancing or
sealing.
The two discarded-output fields are both nonnull only for normalized `response_too_large` and are
otherwise null. `output_was_redacted` is true exactly when `output_redaction_count > 0`; a success
or `response_too_large` attempt may report such replacements, while every other error state requires
false/zero.

Requested provider/model are always nonblank. A successful OpenAI row requires the adapter's exact
nonblank returned `response_model`. PR 3 adds a required nonblank `response_model` to every
successful replay entry and regenerates the fixture with explicit `replay-v1`; fake scripts/provider
construction likewise supply an explicit deterministic returned model. These are per-attempt facts
and are never replaced with the requested model merely to make a run look homogeneous.

`laconian-sanitizer-v1` is exact. It encodes the original valid string and all nonempty patterns as
UTF-8, deduplicates equal byte patterns, and makes one left-to-right, non-rescanning pass over the
original bytes. At each UTF-8 code-point boundary it selects the matching pattern with greatest byte
length; equal lengths use class priority credential, capsule, source root, input root, CWD, home,
local FQDN, local hostname, local username, then exact pattern-byte order. It emits that class's
literal replacement and advances by the original match; emitted replacement bytes are never
scanned again. A pattern present in multiple classes takes the first class. Credential, path, and
username matches are bytewise case-sensitive; FQDN/hostname and URL scheme matching is ASCII
case-insensitive. The output-redaction count is the number of original credential matches selected
by this pass, before any truncation.

The pattern set is constructed once per operation from exact nonempty credential values actually
read for the selected provider; the invocation's lexically normalized absolute capsule, source,
input, CWD, and passwd-database home roots; and each root's descriptor-resolved canonical path.
Path matching is boundary-aware: a root matches only at end of input or when the next byte is the
platform separator, so `/work/a` does not match `/work/ab`. Root spellings with trailing separators
are normalized to the root spelling before deduplication, except the filesystem root itself. On
macOS, both a lexical `/var`, `/tmp`, or `/var/folders` spelling and its descriptor-resolved
`/private/...` spelling are included when they identify the same opened directory. Host patterns
are `socket.getfqdn()`, `socket.gethostname()`, and the hostname's prefix before the first dot,
after stripping one trailing dot; username/home come from `pwd.getpwuid(os.geteuid())`, never
ambient `USER` or `HOME`. Empty values are omitted. The ordered pattern table is immutable for the
operation and is never serialized.

The POSIX filesystem-root pattern `/` is the sole boundary exception: when any known path class is
root, its one-byte pattern matches every `/` byte and emits that class replacement. This
intentionally over-redacts all separators in the degenerate message rather than leaking an
absolute path; it is deterministic and cannot be shadowed by a lower-priority root class.

Before persisted output reaches a ledger, the credential-only form replaces selected matches with
literal `[REDACTED]`. Diagnostics first replace the authority portion of every ASCII case-insensitive
`http://` or `https://` token—from after `//` through the first `/`, `?`, `#`, whitespace, control,
or end—with literal `[URL-AUTHORITY]`, without rescanning that replacement. They then use the
combined credential/local pattern set and replacements `[REDACTED]`, `[CAPSULE]`, `[SOURCE]`,
`[INPUT]`, `[CWD]`, `[HOME]`, `[HOST]`, `[HOST]`, and `[USER]` in the class order above. Local identity values
are used only as sanitizer patterns and are never serialized. After matching, diagnostics remove
Unicode code points U+0000–U+0008, U+000E–U+001F, and U+007F–U+009F; collapse each nonempty run of
U+0009–U+000D or U+0020 to one U+0020; and, if still oversized, retain the longest complete-codepoint
prefix whose bytes plus literal UTF-8 `…[TRUNCATED]` fit the section-5 diagnostic limit.

Provider-controlled non-output identity fields (`response_model`, `request_id`, `finish_reason`, and
an adapter-normalized provider error code) are never silently rewritten. Before persistence they
must be bounded and control-free, contain no credential/path match or URL authority, and contain no
local hostname/FQDN/username match whose adjacent code points (when present) are outside ASCII
letters/digits. A violation converts
the adapter result to constant normalized error kind/message `unsafe_provider_metadata`, with the
unsafe fields omitted; a received response uses `response_received`, while an exception retains its
conservative delivery certainty and can therefore become ambiguous. Requested model remains the
authored manifest value. Tests include equal-length, overlapping, replacement-token, path-alias,
multibyte-boundary, control, whitespace, truncation, hostname/username, URL-authority, and unsafe
identity golden vectors plus replay/SDK strings containing paths and secrets. Generated metadata and
diagnostics must contain neither known local patterns nor known credential values.

Successful output applies the same longest-first known-secret replacement before byte limits,
`output_sha256`, `response_id`, and persistence. It records the replacement count and disclosure
bit above. No digest of the pre-redaction secret-bearing output is stored. Standalone v2 scoring may
record deterministic checks for the persisted text but labels such an attempt redacted, excludes it
from semantic and comparative eligibility, and reports the exclusion count; privacy substitution
must not be mistaken for the provider's exact answer.

## 12. Crash recovery and retry integrity

`verify` never repairs bytes. `resume` first reads exact snapshots of both ledgers under the
exclusive lock, parses their maximal newline-terminated prefixes without mutation, validates every
immutable input and committed relationship, and computes one recovery plan. The normative
write-ahead reconciliation table for each attempt is:

| `request_started` | matching raw | matching `request_finished` | Result |
|---|---|---|---|
| absent | absent | absent | pending; safe to call when selected by the plan |
| present | absent | absent | `AMBIGUOUS_INFLIGHT`; never call automatically |
| present | present | absent | append recovered `request_finished`; no provider call |
| present | present | present | committed attempt |
| absent | present | any | invalid |
| any | absent | present | invalid |

Duplicate starts/finishes, raw-hash mismatch, identity mismatch, a finish before its start, or a
raw row that violates the retry chain is invalid. When all plan items have valid terminal rows but
`generation_completed` is absent, `resume` or `finalize` appends a recovery completion event without
a provider call, referencing the final committed finish as specified in section 11.

After validating the complete recovery plan and before another provider epoch or a seal request,
`resume` and `finalize` append/fsync every derivable missing finish, authentication, ambiguity, and
completion marker in causal order. `finalize` therefore seals a normalized history. An unmatched
start with no raw row has no derivable result marker; it remains markerless
`AMBIGUOUS_INFLIGHT` and may only be sealed with that blocker.

`call_sequence` starts at zero and is consecutive across the entire capsule. Request starts, raw
rows, and finishes have the same sequence, and raw-file order is call-sequence order. The
single-threaded v1 runner permits at most one open request: another request start,
`authentication_stopped`, or `generation_completed` before its finish is invalid. The derived
ambiguous state may still be verified or sealed blocked. A recovered finish points to the original
start event as specified in section 11; it never invents another call identity.

At most one unterminated final fragment is recoverable in each ledger. A torn event fragment may
be removed only when no committed raw row depends on an absent committed start. A torn raw
fragment may be removed, but a durable matching start still classifies the attempt ambiguous. If
both tails exist, the runner evaluates those rules together against the original byte snapshots;
it does not repair one file and then discover that the other makes recovery unsafe. Malformed
newline-terminated JSON, blank lines, or schema-invalid committed records are corruption.

After the entire recovery plan passes, the runner rechecks both exact snapshots and file identities
before the first mutation. If either changed, no file is modified. Under the exclusive cooperative
lock it then performs the approved truncations sequentially, truncating only after the last newline
and fsyncing each file before the next. This sequence is crash-recoverable, not cross-file atomic:
after a crash the next invocation re-derives the plan from durable prefixes before any call. It
appends/fsyncs `tail_recovered` audit events immediately afterward when possible, but their absence
after a process crash does not turn previously unterminated bytes into committed evidence. A
changed input, plan, retry chain, or file identity is rejected before provider construction.

Committed retry histories keep the existing bounded exponential-backoff contract. Resume starts
at the recorded next attempt and does not replay a previously committed backoff sleep. Attempt one
has null `retry_of_attempt`; every later attempt points to its immediate predecessor. A nonterminal
attempt `n` records `backoff_ms = 100 * 2^(n-1)` and a terminal attempt records null. Attempts are
consecutive and never exceed `1 + max_transient_retries`. A terminal record cannot be followed by
another attempt for the same plan item. At most one terminal record exists per plan item.

Dependencies are the sorted PEP 503-normalized installed dependency closure rooted at
`pydantic`, `PyYAML`, `packaging`, and, for OpenAI, `openai`, after evaluating environment markers;
this includes `pydantic-core` and the selected SDK's transport/runtime dependencies without
capturing unrelated installed packages. PR 3 makes `packaging` a direct runtime dependency and uses
its captured implementation to parse/evaluate PEP 508 requirements and markers; marker parsing is
not reimplemented ad hoc. Each selected dependency must be a non-editable, non-local installed
distribution; a `direct_url.json` marking an editable or local source is a preparation error rather
than an unverifiable fingerprint.

`package_version` is the installed `laconian-eval` distribution version and must exactly equal
`laconian_eval.__version__`, source/resolved manifest `runner_version`, capsule `runner_version`,
session package version, and every raw-row runner version. Any disagreement is a preparation or
resume integrity failure before credential access.

For each distribution, the verifier first identifies its one normalized site-packages root. It
hashes every metadata-listed regular member that resolves inside that root, sorted by relative
POSIX path, except caches/bytecode and the volatile metadata members `RECORD`, `INSTALLER`,
`REQUESTED`, and `direct_url.json`. Installation-scheme members outside that root, such as generated
console scripts under `bin/`, are deterministically excluded rather than treated as traversal.
Any selected in-root symlink, missing member, duplicate normalized path, changed descriptor, or
other escape fails. `files_sha256` is the domain-separated root over each included relative path,
byte length, and exact hash. The locked OpenAI environment itself is an acceptance vector, including
metadata that names external console scripts.

Import coverage is part of the fingerprint, not inferred from distribution metadata alone. For
each selected distribution, preparation derives every top-level import name using
`importlib.metadata.packages_distributions()`, resolves its spec under the active interpreter, and
requires one regular origin that is an included member of that distribution's hashed inventory.
Namespace packages, multiple/out-of-root search portions, an unowned origin, or a selected
distribution with executable code but no covered import root are rejected. Before every provider
call, all loaded non-builtin/non-frozen modules are rechecked: `laconian_eval` must resolve to the
captured runner inventory, selected-closure modules to an included dependency member, and standard
library modules to the interpreter's verified `stdlib`, `DESTSHARED`, or admitted `platstdlib`
root; the exact verified console `__main__` below is the sole additional loaded-origin exception. Provider construction
may load the SDK but cannot call it before this post-construction check passes.

`laconian-import-policy-v1` rejects nonempty `PYTHONPATH` or `PYTHONHOME` and an enabled user site.
At the first harness preflight it validates every already-loaded non-builtin/non-frozen module
origin under the rules below, before changing bootstrap state. The sole exception is console-mode
`sys.modules["__main__"]`, governed by the verified launcher below. It then removes exactly one
launcher-only entry and its importer-cache entries: either empty/CWD for a module launch whose
loaded `laconian_eval` origin is already captured, or the descriptor-resolved parent of regular
`sys.argv[0]` when installed metadata has exactly one `laconian` console entry point mapped to
the current target `laconian_eval.cli:entrypoint`. Any other launcher entry fails. It also removes only the nonexistent
CPython placeholder `<parent-of-stdlib>/python<major><minor>.zip`, after a no-follow absence check;
an existing zip is unsupported. The runner then canonicalizes active `sys.path` to this ordered
allowlist: `sysconfig`'s descriptor-verified `stdlib` beneath `sys.base_prefix`; distinct nonnull
`DESTSHARED` beneath that same base prefix; the captured runner package parent in path mode; then the verified site-packages roots that own
selected dependency inventories. Equal roots deduplicate at first occurrence. Every other path fails.
Built-in and frozen standard-library modules are allowed. A same-named module in CWD, user site, or
any other root is shadowing and fails even when it has not yet been imported. Literal host roots
are not serialized; the fixed policy literals, covered origin-member records, interpreter
identity, dependency inventories, `platstdlib_mode`, and bootstrap hash bind the decision. A
distinct `platstdlib` is always recorded `omitted` and rejected if already active; it is not added
merely because `sysconfig` names it. `DESTSHARED` is mandatory for CPython extension-module
resolution; a platstdlib equal to stdlib records `same_as_stdlib`.

For `launcher_mode=console_script`, `__main__.__file__` and `sys.argv[0]` must identify the same
no-follow regular file. Its first line is an absolute shebang whose descriptor-resolved executable
equals `sys.executable`; all remaining LF-framed UTF-8 bytes must equal the exact standard generated
wrapper that imports only `sys` and `laconian_eval.cli.entrypoint`, performs only the two standard
`-script.pyw`/`.exe` `argv[0]` suffix normalizations, and exits by calling `entrypoint()`. The
normalized template replaces the shebang payload with literal `#!<CURRENT_INTERPRETER>` before
hashing; that digest is `launcher_template_sha256`, so a relocated equivalent virtualenv remains
compatible without serializing its path. This verified `__main__` is the only origin outside the
inventories and remains loaded but cannot provide application behavior beyond the wrapper.
`launcher_mode=module` requires `__main__` itself to be a captured runner member and requires null
launcher digest. Console mode requires the fixed digest; both fields participate in the runtime
fingerprint.

The exact normalized console template, including its final LF, is:

```text
#!<CURRENT_INTERPRETER>
# -*- coding: utf-8 -*-
import sys
from laconian_eval.cli import entrypoint
if __name__ == "__main__":
    if sys.argv[0].endswith("-script.pyw"):
        sys.argv[0] = sys.argv[0][:-11]
    elif sys.argv[0].endswith(".exe"):
        sys.argv[0] = sys.argv[0][:-4]
    sys.exit(entrypoint())
```

Its required SHA-256 is
`afdb677819f87d2c8e8af0eb2461ea1856b13dec27768546af0175c376ee493d`.

The supported import bootstrap is deliberately narrow. `.egg-link` is rejected. A path-only `.pth`
entry is permitted only when its sole target resolves to the captured `laconian_eval` package parent
and records `runner_import_mode=path`; a wheel install records `wheel`. The only executable `.pth`
exception is virtualenv's exact single `import _virtualenv` bootstrap. Its `.pth` bytes and regular
`_virtualenv.py` bytes form `virtualenv_bootstrap_sha256`, and `_virtualenv._Finder` is then the only
nonstandard ambient meta-path finder allowed before the harness guard is installed. Any other executable `.pth`, generated editable
finder, nonstandard path hook/finder, or import origin outside the committed inventories fails
preparation. No host path is serialized in this projection.

Immediately before the harness guard is added, `sys.meta_path` is exactly optional hashed
`_virtualenv._Finder`, then CPython `BuiltinImporter`, `FrozenImporter`, and `PathFinder` by object
identity. `sys.path_hooks` contains exactly the standard `zipimport.zipimporter` hook followed by
the standard `FileFinder.path_hook`; the zip hook may remain but no active/existing zip path or zip
importer may. Importer-cache keys must resolve equal to or beneath an allowed path, and values are
only the standard `FileFinder` (or null negative cache); entries for removed bootstrap paths are
purged. These ordered identities are part of the guarded runtime policy even though host paths are
not serialized.

The runner snapshots and validates `sys.path`, `sys.meta_path`, `sys.path_hooks`, and every active
`sys.path_importer_cache` key/finder at preparation. It repeats that complete check after provider
construction and immediately before every provider call, then validates every module loaded since
the preceding check under the same ownership/origin rules. A provider cannot use an inserted
finder/path or a deferred import to execute an out-of-inventory module. The only nonstandard
finder exception remains the exact hashed virtualenv bootstrap above.

Before provider construction, the runner installs captured `_LaconianImportGuard` as the first
meta-path finder and keeps it active through result normalization. Its exact defining runner file
is in `runner-source.json`; `guard_source_sha256` is the SHA-256 of that captured file. For every
import, before any loader code executes, the guard queries only the fixed permitted builtin,
frozen, optional hashed-virtualenv, and standard path finders; rejects namespace, zip, unknown, or
out-of-policy specs; validates regular origin membership against the runner/dependency inventories
or verified interpreter stdlib roots; and returns a proxy loader that repeats descriptor identity
and origin checks immediately before and after `exec_module`. The guard cannot delegate to an
ambient finder. Removing/reordering the guard, changing allowed finders/hooks/paths, or loading an
unowned module aborts before provider construction or, during a call, before that module executes.
After provider construction, immediately before the call, and immediately after return, the runner
also rechecks guard identity/order, hooks, paths, importer cache, and all loaded module origins.

The same captured module installs an application-owned `sys.addaudithook` before installing the
finder; `audit_hook_source_sha256` hashes its defining file and normally equals the guard digest.
Python exposes no removal API for this hook. On every `import` audit event, before resolution, it
requires the exact guard object to remain first and the fixed `sys.path`, `sys.meta_path`,
`sys.path_hooks`, and permitted finder identities to remain unchanged; otherwise it raises and the
import does not resolve. A provider/SDK therefore cannot remove or precede the guard and then lazy
load uncommitted code before the next post-call check. Installation runs a captured sentinel-import
self-test that must prove the audit hook observed the event and the guard rejected a synthetic
out-of-policy origin; failure aborts before provider construction.

Import-root records are unique and sort by UTF-8 `(distribution, module, origin_member)`.
`virtualenv_bootstrap_sha256` is null when the exception is absent; otherwise it is
`stable_digest("laconian-import-bootstrap-v1", {"pth_sha256": SHA256(exact .pth bytes),
"module_sha256": SHA256(exact _virtualenv.py bytes)})`. These exact fields, including both policy
literals, extension policy/mode, guard/audit-hook digests, and runner import mode, participate in
`import_environment` and the runtime fingerprint.

Fake/replay require `transport_policy=offline` and both SDK fields null. OpenAI requires
`transport_policy=openai-direct-v1`: the SDK client receives the explicit public base URL, explicit
timeout, `max_retries=0`, empty organization/project/admin/webhook settings, and an explicit
`DefaultHttpxClient(trust_env=False)`. Proxy, `NO_PROXY`, and SSL-certificate environment variables
therefore cannot alter its transport; OpenAI-specific custom-header ambient configuration remains a
fail-closed configuration error. Tests set ambient proxy/certificate variables and prove they do not
reach client construction. `uv_lock.sha256` is nonnull exactly when availability is
present. `checkout_binding=bound` means a supplied source inventory byte-matches the installed
runner snapshot. PR 3 never runs a Git command that examines worktree content: repository-controlled
clean filters and filesystem-monitor configuration can execute arbitrary programs even during an
apparently read-only `git status`. The PR 3 producer therefore records `git_state=unavailable` and
`git_commit=null` for every byte-bound source. The `clean|dirty` alternatives remain in the schema
for a future producer that implements a passive, no-execution Git reader; a compatible verifier may
parse them, but this producer does not emit them. `checkout_binding=unbound` means a source root was
supplied but did not match and requires unavailable/null Git and lock attribution.
`checkout_binding=unavailable` means no source root was supplied and has the same unavailable/null
attribution. Git attribution, when produced by a future compatible producer, and lockfile data are
nonnull only for a bound checkout. The optional container
digest is accepted only from an explicit `--container-image-digest sha256:<64-hex>` argument; no
ambient container metadata is read.

The installed-source snapshot is discovered from the single verified `laconian_eval` package root.
It recursively includes normalized regular `*.py` files and an optional exact `py.typed`; it ignores

Each dependency root is `stable_digest("laconian-distribution-files-v1", {"distribution": name,

`--source-root` supplies the project fixture root for file-backed `if`/Caveman arms and, when

Arbitrary Git remotes are never captured, and lockfile bytes are never copied because they may
contain private URLs.

Git, lockfile, container, and installed-distribution digests are sealed producer commitments: a
checkout-free verifier validates their schema/relationships but cannot recompute absent external
bytes. Copied runner/input hashes are self-contained and are always recomputed. Resume recomputes
the required installed-environment fingerprints before any credential access.

Provider SDK version is read through package metadata without constructing the provider. A selected
OpenAI manifest requires the SDK distribution to be installed at preparation; absence is a local
configuration error before capsule publication, not a live-provider operation.

Before credential access or provider construction, `resume` requires equality of the resolved
manifest hash, runner-source digest, exact package version, adapter digest, runtime-dependency
versions/fingerprint, fixed transport policy, provider SDK identity when applicable, Python implementation, and Python
major/minor. Python patch, OS release, and architecture are recorded in every `execution_started`
session environment for diagnosis but do not by themselves block resume. A mismatch creates a new
run; it never mutates the old capsule.

A clean or dirty source may be byte-bound because its exact installed-source snapshot is recorded
and disclosed independently of Git worktree classification. PR 3 reports that classification as
unavailable rather than risking repository-controlled process execution. This is strong source
provenance, not proof that already imported Python code objects or native dependencies equal those
bytes, and PR 3 does not turn the disclosure into claim readiness.

A compatible verifier parses `CapsuleV1` independently of the current `RunManifest` validator.
Read-only integrity verification does not require the current package version to equal the
producer version. Execution and semantic recomputation do require the captured producer identity.

PR 3 produces a data-self-contained capsule, not a fully offline executable distribution. A copied
sealed capsule can be verified without its source checkout by an installed compatible verifier.
Resuming without the checkout additionally requires a separately installed producer whose exact
required identity matches the capsule; the copied source inventory is evidence and is not executed
in place. A bundled wheel/standalone verifier and clean-environment recomputation belong to PR 6.

## 14. Atomicity, ownership, and no-overwrite

Preparation writes all snapshots, indexes, plan, environment, empty ledgers, and initial event to
the exact operation-owned sibling `<results-root>/.laconian-stage.<operation_id>` and publishes it as
`<results-root>/<run_id>`; the directory name is convenient transport metadata, not run identity.
The results root is a verified non-symlink directory; creators
serialize on `<results-root>/.laconian-create.lock`, opened with mode `0600`, no symlink following,
descriptor-type validation, and an exclusive advisory lock. Under that lock preparation fsyncs
files and directories and publishes with one descriptor-relative atomic directory no-replace
operation: Linux `renameat2(RENAME_NOREPLACE)` or macOS
descriptor-relative `renameatx_np(..., RENAME_EXCL)`. Path-based `renamex_np` and
check-then-ordinary-rename fallbacks are forbidden. It then
fsyncs the already opened results-root directory descriptor. `capsule.json` is written
last inside staging and is the prepared-capsule marker. A failed no-replace rename publishes
nothing: the operation validates and may remove only its owned staging directory, reports a
collision/configuration failure, and never prints or claims an existing destination. If rename
succeeds but results-root fsync fails, the now-visible operation-owned capsule is preserved, its
path is printed for explicit recovery, and the command exits without provider construction. In
both cases no call occurs. Provider construction happens only after durable publication and full
prepared-stage verification.

Mutation is additionally gated by exact `FilesystemClassV1`, not inferred from the capability
probes. On Linux, descriptor `fstatfs` magic must be ext2/3/4 (`0xEF53`), XFS (`0x58465342`), Btrfs
(`0x9123683E`), or ZFS (`0x2FC12FC1`); the recorded classes are respectively `ext-family`, `xfs`,
`btrfs`, and `zfs`. On macOS, descriptor `fstatfs` must report `MNT_LOCAL` and exact type `apfs` or
`hfs`, recorded as `apfs` or `hfsplus`. NFS, SMB/CIFS, FUSE, overlay, tmpfs, network, removable
nonlocal, and every unknown type are rejected before staging publication or mutation even if an
individual probe happens to pass. Linux `/proc/self/mountinfo` and the descriptor device/mount ID
must agree with the selected local mount; an absent, ambiguous, or conflicting classification is
unsupported. The class is recorded in `EnvironmentV1` and each `SessionEnvironmentV1`; a mutator
recomputes it for the current capsule parent and requires equality with that session record.

Every preparation performs bounded, harmless capability probes under its operation-owned staging
path; no durable prior result is trusted. For advisory locking, one process holds the probe lock
while a second process must observe a contended nonblocking acquisition, after which release and
reacquisition are verified. The same probe checks the platform's atomic directory no-replace rename
against a concurrently existing destination, atomic hard-link no-replace, regular-file fsync, and
directory fsync. Preparation
removes and fsyncs the probe entries while still holding the creator lock. Any unsupported or
indeterminate primitive fails before capsule publication; a later finalizer never discovers that
its required durability primitive was unavailable only after provider calls occurred.

Owned-path creation, inspection, rename, and link operations are descriptor-relative to already
opened/validated parent directories and use no-follow/exclusive primitives. A path is not deemed
safe merely because an earlier string-based check succeeded.

Every mutating command acquires an exclusive kernel advisory lock on the persistent
`.laconian.lock` file before reading any capsule artifact. Unsealed verification requires that file
and acquires a shared lock or returns `busy`; it never observes a cooperating writer's partial
state. Lock state is tied to the open descriptor and is released automatically on process death.
The lock is opened without following symlinks and is verified as the expected regular file before
the advisory operation.

Presence of `seal.json` selects sealed verification and never falls back to mutable verification if
the seal is invalid. On an allowlisted local filesystem, an existing lock is taken shared. On an
unsupported transport filesystem, sealed verification ignores/excludes the operational lock file
whether it exists or not and uses the lockless descriptor-snapshot algorithm; the same algorithm is
used on an allowlisted filesystem when a sealed transport copy omits the lock. It recursively enumerates the
complete relative path/type/identity set, open seal and inventoried files without following links,
compare identity/size metadata before and after bounded reads, recompute every byte hash, then
recursively re-enumerate and compare the complete path/type/identity set and re-read the seal. Any change produces
`unstable_snapshot`; it is not reported valid. This supports read-only transport but makes no claim
against a malicious process continuously replacing both capsule and seal.

PR 3 supports capsule mutation only on a `FilesystemClassV1` allowlisted local macOS/Linux
filesystem that also passes the advisory-lock, atomic directory no-replace, hard-link no-replace,
file-fsync, and directory-fsync probes. NFS and every other unclassified filesystem fail closed;
the probes are necessary but never substitute for classification. A non-cooperating process that
ignores the lock remains outside the concurrency guarantee.

Every mutating command on an existing unsealed capsule, and the idempotent sealed-finalizer residue
cleanup, repeats the same second-process and durability probes in an operation-owned hidden sibling
under the capsule's parent before touching capsule bytes, then removes/fsyncs that probe. This
deliberately supports a transported unsealed capsule only when its new local filesystem
independently satisfies the contract; read-only verify does not require mutation capabilities.
Unsealed verify still needs the allowlisted filesystem and shared-lock guarantee. A sealed capsule
may instead use the lockless immutable snapshot algorithm on an unsupported transport filesystem;
no mutation or idempotent-finalizer cleanup is permitted there.

Verification treats unexpected writability or broader modes as a security warning. It does not
call a copied capsule corrupt merely because another supported OS represents permission bits
differently. Copying or renaming an unsealed capsule is supported only while a shared lock is held
and the capsule is quiescent; a sealed capsule may be copied without its persistent lock file, and
the verifier ignores that operational file when computing identity.

The only mutable files before sealing are append-only `events.jsonl` and `raw.jsonl`; each permits
only the validated final-fragment recovery exception in section 12. Everything else is write-once. Existing destinations
always fail; there is no `--force`. Cleanup removes only an operation-owned staging path after
validating its identity. Orphan staging cleanup is a separate explicit maintenance operation and
never targets a published capsule.

After sealing, every evidence-mutating command refuses the capsule. The only operational exception
is idempotent `finalize` on a local byte-valid seal: under the existing lock it may remove exactly
the matching same-content seal temporary and fsync the directory, without changing evidence bytes.
Corrections and reruns create new capsules and may declare the superseded capsule hash in future
attachment/publication metadata.

## 15. CLI contract

```bash
laconian validate <manifest-or-case>
laconian plan <manifest> --results-root <directory> [--input-root <directory>]
              [--source-root <directory>]
              [--container-image-digest sha256:<64-hex>]
laconian run <manifest> --results-root <directory> [--input-root <directory>]
             [--source-root <directory>]
             [--container-image-digest sha256:<64-hex>]
laconian resume <run-directory>
laconian verify <run-directory> [--require <stage>]
laconian finalize <run-directory> [--seal-incomplete]
```

`validate` preserves the existing read-only case/source-manifest validation command. It dispatches
strictly among response case, activation case, source-manifest v1, and source-manifest v2 by their
discriminating fields/version, checks the document schema and path grammar, and creates no capsule;
it does not resolve or capture referenced files, read credentials, or access the network.

`plan` performs local preparation and creates a `PREPARED` capsule, but it never reads an API-key
value, constructs a provider, or makes a provider call. It prints the capsule path once on stdout;
stderr summarizes case/scenario/locale/arm/repetition counts, total planned requests, hashes,
purpose, claim intent, and known operational disclosures. Cost is `n/a`; maximum output tokens are
not a defensible price estimate.

`run` is the convenience composition of preparation followed by `resume`. It prints the capsule
path as soon as preparation succeeds so a later failure is recoverable.

`resume` advances provider execution only for a prepared, interrupted, or fully covered but
missing-completion-event capsule. It uses no external manifest, cases, arms, replay fixture, or
checkout path. It verifies
producer identity and immutable inputs before reading a secret or constructing a provider.
For an authentication/ambiguous capsule with a missing derived-state marker, `resume` may append
only that recovery marker and then exits operationally; it never constructs a provider or advances
the plan. `SEALING_INTERRUPTED` accepts only `finalize`.

`verify` is strictly read-only. On a quiescent capsule it validates every lifecycle stage. If a
writer owns the exclusive lock, a nonblocking shared-lock attempt returns the operational result
`busy`; it does not inspect a partial snapshot. Without `--require`, an internally consistent
incomplete capsule exits successfully and reports its state/blockers. `--require
generation-complete` and `--require sealed` fail when the requested stage is absent. Corruption
always fails.

Its canonical stdout object is strict `VerifyResultV1`:

```yaml
schema_version: "1"
status: valid | invalid | busy | unsupported
run_id: <UUID or null>
state: <PREPARED | INTERRUPTED | AMBIGUOUS_INFLIGHT | AUTHENTICATION_STOPPED |
        GENERATION_COMPLETE | SEALING_INTERRUPTED | SEALED_COMPLETE | SEALED_BLOCKED or null>
capsule_sha256: <sha256 or null>
missing_plan_item_ids: [<sha256>, ...]
operational_blocker_codes:
  [<never_started | interrupted | ambiguous_inflight | authentication_stopped>, ...]
warnings:
  [<broader_permissions | permission_representation_differs |
    producer_runtime_differs | lock_file_omitted_for_sealed_transport>, ...]
first_error:
  code: <unsupported_schema | resource_limit | unexpected_path | missing_path |
         unsafe_path_type | unstable_snapshot | noncanonical_json | invalid_model |
         hash_mismatch | identity_mismatch | plan_mismatch | history_mismatch |
         retry_mismatch | lifecycle_mismatch | seal_mismatch | unsupported_filesystem |
         io_error>
  path: <normalized capsule-relative POSIX path or null>
  sequence: <nonnegative event/raw sequence or null>
  explanation: <sanitized nonblank diagnostic within the section-5 bound>
  # or the entire first_error value is null
```

For `valid`, run ID and state are nonnull, `first_error` is null, and `capsule_sha256` is nonnull
exactly for either sealed state. Missing IDs and blockers are the exact derived sets. For `invalid`,
all artifact-derived scalar fields are null and all three arrays are empty; `first_error` is
nonnull and its code is not `unsupported_filesystem`. For `busy`, the same fields are null/empty
and `first_error` is null. For `unsupported`, they are null/empty and `first_error` has exactly
`code=unsupported_filesystem`, null path/sequence, and a bounded platform explanation. This last
status applies only when unsealed verification cannot obtain the required local-filesystem
contract; lockless sealed verification remains available on transport filesystems.

Missing IDs sort by UTF-8 bytes; blockers use the fixed seal order; warnings use their displayed
enum order. Every array is duplicate-free. Error path never contains an absolute/host path, and
explanation passes `laconian-sanitizer-v1`. `--require` does not rewrite an otherwise `valid`
object: an unmet requested stage prints the same integrity result and changes only the exit code to
2. Busy and unsupported also exit 2; valid exits 0 unless `--require` is unmet; invalid exits 2.

`finalize` seals a complete capsule by default. `--seal-incomplete` is required to preserve a
never-started, interrupted, ambiguous, or authentication-stopped capsule as `SEALED_BLOCKED`. It
cannot convert missing attempts into outcomes or remove blockers. Finalization appends and fsyncs
`seal_requested`, derives the complete seal from the now-frozen pre-seal files, then atomically
publishes the single `seal.json` described in section 17. A retry reuses the one committed request;
its new CLI `operation_id` does not replace the durable `seal_transaction_id`. Multiple
`seal_requested` events are invalid, and no execution/resume event may follow it.
`finalize` is the only mutator accepted in `SEALING_INTERRUPTED`.
It is also accepted on `SEALED_COMPLETE`/`SEALED_BLOCKED` solely for the residue/fsync operation in
section 14; any seal/content mismatch fails without cleanup.

CLI stdout/stderr and exit status are stable:

- `plan`, `run`, `resume`, and `finalize` print the absolute capsule path exactly once per CLI
  invocation as soon as a valid target capsule is known; all diagnostics go to stderr;
- `verify` prints one canonical JSON object on stdout;
- exit `0` means the requested operation/stage succeeded, including a valid incomplete `verify`
  without `--require`;
- exit `1` means an operational run stop after a capsule path exists, including missing provider
  construction, post-publish directory-fsync failure, authentication stop, interruption, or
  ambiguous in-flight state;
- exit `2` means usage/configuration error, integrity failure, collision/no-overwrite, busy lock,
  unsupported unsealed filesystem, unmet `--require`, or seal mismatch.

## 16. Staged verification

Verification runs in this order:

1. **Structure:** owned-path allowlist, regular files, no symlinks, schemas, permission warnings,
   and run identity.
2. **Static inputs:** canonical manifest, input index, exact case/arm/replay/protocol bytes,
   source/canonical hashes, environment, runner inventory, and lockfile availability/digest.
3. **Case index:** unique case/scenario identities, source ordinals, locale/category fields, and
   complete case/prompt hashes.
4. **Plan:** canonical JSONL framing, plan hash, Cartesian coverage, order, block positions,
   pairing identities, and request hashes.
5. **Events/raw:** canonical framing, monotonic event sequence, request/result matching, raw
   identity, retry lineage, redaction bounds, returned-model disclosure, and output/usage fields.
6. **Lifecycle:** lock-aware derived state, completion coverage, authentication stop, ambiguous
   requests, and explicit missing plan IDs.
7. **Seal:** seal schema, generation-state consistency, sorted inventory, derived root digest, and
   absence of unexpected files. Exactly one temporary is allowed only when its transaction ID
   matches the sole seal request. Without `seal.json` it is interrupted finalization; with a seal it
   must contain the same bytes and is removable operational residue.

The verifier stops at the first structural trust failure and publishes no repaired artifact. It
returns structured reason codes plus a concise human explanation. Within a stage, files are checked
in relative-path UTF-8 byte order, JSONL records in sequence order, and fixed schema fields in their
displayed model order, so the first error is deterministic. Another OS or verifier version is
diagnostic metadata, not a byte-integrity failure.

## 17. Atomic seal and future extension contract

`seal.json` is strict `SealV1`. It contains:

```yaml
seal_schema_version: "1"
run_id: <uuid>
seal_transaction_id: <uuid>
generation_status: complete | incomplete
structural_integrity: valid
missing_plan_item_ids: [<sorted IDs>]
operational_blocker_codes:
  - never_started | interrupted | ambiguous_inflight | authentication_stopped
never_started_detail: null | credential_unavailable | provider_unavailable | operator_abandoned
disclosures:
  source_state: clean | dirty | unbound | unavailable
  returned_models: [<sorted distinct nonblank values>]
  usage_availability_counts: {complete: <n>, partial: <n>, unavailable: <n>}
  redacted_output_attempt_count: <nonnegative integer>
  redacted_output_replacement_count: <nonnegative integer>
  dataset_ids: [<sorted IDs>]
  protocol_binding_ids: [<sorted IDs>]
final_event_sequence: <integer>
raw_attempt_count: <integer>
sealed_at: <UTC RFC 3339>
files:
  - path: <relative POSIX path>
    byte_length: <integer>
    sha256: <sha256>
```

The sorted inventory contains every owned pre-seal regular file except `.laconian.lock`; it does
not contain `seal.json` or an operation temporary. A plan item is resolved only by a valid terminal
`success`, `retry_exhausted`, or `provider_rejected` row. `missing_plan_item_ids` is exactly every
other materialized plan ID, including the authentication/ambiguous item itself and every later
uncalled item. `complete` requires no missing item and an empty blocker array; `incomplete` requires
at least one missing item and exactly one blocker selected by the quiescent-state precedence:
`never_started` for a quiescent `PREPARED` no-call state, `ambiguous_inflight` for ambiguity,
`authentication_stopped` for authentication, and `interrupted` for every other incomplete history.

`never_started` alone requires `never_started_detail`: it is the latest valid
`execution_blocked.reason` when one exists, otherwise `operator_abandoned`. Every other blocker
requires the detail to be null. The seal transaction ID and expected generation status equal the
sole `seal_requested` payload; `prior_event_sequence` equals that event's sequence minus one,
`final_event_sequence` equals its sequence, `sealed_at` equals its timestamp, and
`raw_attempt_count` equals the exact number of committed LF-framed raw rows. These rules leave no
producer choice in the seal fields. Dirty source, mixed returned models, partial usage, dataset
roles, protocol declarations, and output redaction are disclosures, not generation blockers or
claim-readiness decisions.

Seal `source_state` is derived exhaustively: `unbound` when `checkout_binding=unbound`; `clean` or
`dirty` when binding is `bound` and Git has that state; and `unavailable` when binding is
`unavailable` or when a byte-bound source has `git_state=unavailable`.

All set-like arrays are duplicate-free. Missing plan IDs, returned models, dataset IDs, protocol
IDs, and inventory paths sort by their exact UTF-8 bytes. Blockers sort by the fixed enum order
`never_started`, `interrupted`, `ambiguous_inflight`, `authentication_stopped`. Usage counts cover
every raw attempt, including retries and errors, and their sum equals `raw_attempt_count`.
`returned_models` is the distinct set from successful raw attempts only. The redacted-attempt count
is the number of raw rows whose disclosure bit is true; the replacement count is the exact sum of
their `output_redaction_count` values.

After `seal_requested` is committed, finalization verifies the frozen snapshot and uses that
event's timestamp as `sealed_at`, making retries deterministic. It constructs exact canonical
`seal.json` bytes, writes and fsyncs `.seal.<seal_transaction_id>.tmp`, then publishes the final name with
an atomic no-replace hard-link operation on the supported local POSIX filesystem. It unlinks the
temporary and fsyncs the directory. A crash before the link leaves an unsealed, retryable capsule
plus an ignorable temporary whose transaction ID must match the committed seal request; a crash after
the link leaves the complete seal, possibly with the same harmless hard-link temporary. An
existing `seal.json` must match byte-for-byte for idempotent verification and is never overwritten.

Without a seal, retrying `finalize` re-derives the frozen bytes. An exact complete temporary is
linked; a partial/mismatching one is removed and recreated only after descriptor-safe identity
validation. With a seal, a temporary must have identical content (normally the same inode), after
which idempotent `finalize` removes it and fsyncs the directory. These are finalization retries, never
generation retries.

The externally usable capsule identity is
`capsule_sha256 = SHA256(exact canonical seal.json bytes)`. It is derived and reported, not stored
inside its own preimage. The seal inventory plus the already-bound hashes in `capsule.json` commits
to all generation bytes. It provides tamper evidence and self-consistency, not authorship or proof
that an author never replaced both capsule and seal; a release digest or signature belongs to the
publication layer.

PR 3 deliberately does not define or test an attachment envelope. PR 4/5 must preserve these
extension constraints when their actual estimands and judge workflows are known:

- every immutable attachment forms an acyclic dependency graph rooted in one or more
  `capsule_sha256` values and records exact dependency hashes;
- attachment IDs use a specified canonical preimage that excludes the ID itself;
- protocols bind by captured `binding_id`, with declared scope and evaluation timing;
- hard/cost evidence targets `attempt_id` or `plan_item_id`, semantic evidence targets
  `response_id`, preference evidence targets a declared pair plus both response IDs, and inference
  targets a comparison plus exact dependency roots;
- blind judge requests use a separate random `blind_id` and omit arm, provider, model, position,
  token, length, and cost metadata, while documentation still discloses residual style leakage;
- row numbers, directory names, and mutable prose are never evidence identities.

## 18. Compatibility and migration

- Existing source manifest schema v1 remains accepted and is upgraded only during preparation to
  resolved manifest v2 with the explicit non-claim defaults in section 8. New capsule fields are
  not silently added to the strict v1 model.
- Capsule schema v1, source manifest schemas v1/v2, event schema v1, and attempt schema v2 are
  separate models and versions.
- Capsule attempt schema v2 is required for new capsules. A strict internal `ScorableAttempt`
  projection carries source schema, raw-record digest, run/manifest/case/arm/repetition/attempt
  identity, terminal/output/error/usage fields, and response identity. V1 derives its current
  response ID; v2 must use the persisted ID. Serialization dispatches to unchanged
  `ScoredAttemptV1` or strict `ScoredAttemptV2`; no v2 row is coerced into v1 or loses
  delivery/usage provenance.
- Standalone command forms are unambiguous:

  ```text
  laconian score <raw-v1> --cases <case> [--cases <case> ...]
                 [--judgments <yaml>] --output <sidecar-directory>
  laconian score <capsule-v2> [--judgments <yaml>] --output <sidecar-directory>
  laconian report <scored-v1> --output <sidecar-report>
  laconian report <scored-v2> --capsule <capsule-v2> --output <sidecar-report>
  ```

  V1 requires one or more repeatable `--cases` flags. Files are loaded in flag order, their cases
  form one strict aggregate, and duplicate case IDs or a scenario/locale pair split across files
  fail under the same global case invariants. V2 forbids `--cases`: it verifies the supplied
  capsule with `generation-complete` required and reads only its captured case index/files,
  manifest, arms, and raw ledger. The v2 report requires that same capsule so retry usage and raw
  provenance are recomputable. Judgment targeting dispatches derived-v1 versus persisted-v2
  response identity. Both paths remain labeled nonpublication.

`ScoredAttemptV2` is strict:

```yaml
schema_version: "2"
raw_record_sha256: <sha256 of the exact canonical LF-free RawAttemptV2 row>
raw: <strict terminal RawAttemptV2 object>
checks:
  - {name: <nonblank string>, passed: <boolean>, detail: <bounded string>}
hard_pass: <boolean>
redaction_excluded: <boolean>
semantic_pass: <boolean or null>
judgment_id: <sha256 or null>
judge_provenance:
  provider: <nonblank string>
  model: <nonblank string>
  prompt_sha256: <sha256>
  # or the entire judge_provenance value is null
```

The raw hash must match the embedded canonical raw object and that exact row in the capsule.
`hard_pass` equals provider success and the conjunction of every deterministic check.
`redaction_excluded` equals `raw.output_was_redacted`. Semantic fields are all null or all nonnull,
are legal only on a successful hard pass with nonnull persisted `raw.response_id`, and when present
`judgment_id` must equal that exact response ID. They must all be null when redaction-excluded. A
redacted result may retain deterministic checks but is never semantically judged or
comparison-eligible.

`UsageAvailabilityCountsV2` has exactly nonnegative integer fields `complete`, `partial`, and
`unavailable`. `ArmMetricsV2` is strict:

```yaml
arm: baseline | concise | caveman | if
total: <nonnegative integer>
hard_passed: <nonnegative integer>
semantic_passed: <nonnegative integer or null>
semantic_judged: <nonnegative integer>
provider_errors: <nonnegative integer>
retry_attempts: <nonnegative integer>
exact_violations: <nonnegative integer>
format_violations: <nonnegative integer>
median_output_tokens: <finite nonnegative number or null>
median_output_characters: <finite nonnegative number or null>
token_observed: <nonnegative integer>
redacted_output_exclusions: <nonnegative integer>
usage_availability: {complete: <int>, partial: <int>, unavailable: <int>}
price:
  input_usd: <finite nonnegative number>
  cached_input_usd: <finite nonnegative number>
  output_usd: <finite nonnegative number>
  total_usd: <finite nonnegative number>
  # or the entire price value is null
```

`total` counts terminal rows for that arm; `hard_passed <= total`, provider errors are terminal
error rows, and retry attempts are nonterminal rows. Usage counts cover every raw row for the arm,
so their sum equals `total + retry_attempts`; redaction exclusions count terminal successful rows
that both hard-pass and are redaction-excluded. Semantic judged is at most hard-passed minus redaction exclusions;
semantic passed is null exactly when semantic judged is zero and otherwise is between zero and the
judged denominator. Medians use only successful gate-eligible, non-redacted terminal rows and are
computed independently: character median is null exactly when that set is empty; `token_observed`
counts rows in that set with nonnull `usage.output_tokens`, and token median is null exactly when
`token_observed` is zero. Price total equals the exact sum of its three components.

`RunSummaryV2` is strict:

```yaml
schema_version: "2"
source_attempt_schema_version: "2"
run_id: <UUID>
manifest_sha256: <sha256>
capsule_sha256: <sha256 or null>
raw_sha256: <sha256 of exact raw.jsonl bytes>
scored_sha256: <sha256 of exact scored.jsonl bytes>
quality_gate: hard | semantic
raw_attempts: <nonnegative integer>
terminal_records: <nonnegative integer>
runner_versions: [<exactly one nonblank version>]
case_definitions:
  - {case_uid: <sha256>, case_id: <nonblank string>, sha256: <sha256>}
providers: [<nonblank string>, ...]
usage_availability: {complete: <int>, partial: <int>, unavailable: <int>}
redacted_output_attempts: <nonnegative integer>
redacted_output_replacements: <nonnegative integer>
arms: [<ArmMetricsV2>, ...]
paired:
  left_arm: if
  right_arm: concise
  eligibility_gate: hard | semantic
  candidate_pairs: <nonnegative integer>
  eligible_pairs: <nonnegative integer>
  token_eligible_pairs: <nonnegative integer>
  excluded_redacted_pairs: <nonnegative integer>
  median_output_token_delta: <finite number or null>
  median_output_character_delta: <finite number or null>
price_snapshot: <strict PriceSnapshotV1 or null>
judge_provenance: [<strict JudgeProvenance objects>, ...]
```

The capsule hash is nonnull exactly when the source capsule was sealed in the score command's
validated descriptor snapshot. A null hash remains valid if the same capsule is sealed later,
provided report recomputation proves every bound pre-seal/raw byte unchanged; it conveys no
immutable capsule identity. Raw attempts count every ledger row; terminal records equal scored rows; global and per-arm usage counts partition the
corresponding raw rows, and global usage counts sum to `raw_attempts`. Runner versions contain only
the capsule runner. Case definitions exactly cover the case index and sort uniquely by UTF-8
`case_uid`; providers are the sorted distinct values from every raw row; judge provenance is the
sorted unique `(provider, model, prompt_sha256)` set attached to scored rows; arms contain exactly
one entry per manifest arm in manifest order. Redacted-output attempts count every raw row whose
bit is true, while replacements are the exact sum of all row replacement counts. Candidate pairs are
the materialized same-case/repetition `if`/`concise` pairs, and eligible pairs require both sides to
pass the selected gate and neither side to be redaction-excluded. Deltas remain `concise - if`, so
positive means `if` is shorter. Character delta uses every eligible pair and is null exactly when
`eligible_pairs` is zero. `token_eligible_pairs` counts eligible pairs where both output-token
counts are nonnull, is at most `eligible_pairs`, and token delta is null exactly when that count is
zero. `excluded_redacted_pairs` counts candidate pairs with at least one redaction-excluded side,
regardless of whether either side also fails the selected gate.

Every v2 arm price is `n/a` unless a dated manifest price snapshot exists and every raw attempt for
that arm has complete core usage with cache accounting either `reported` or `not_applicable`.
`partial`, `unavailable`, or `not_reported` usage makes that arm's price null; no missing value is
converted to a token count. Cost sums all calls including retries/errors. For each row with
`reported` cache accounting, `uncached = input_tokens - cached_input_tokens`, input cost uses the
uncached price, and cached cost uses the cached price; a positive cached count with null cached
rate makes price `n/a`, while a reported zero yields exact cached cost zero. For `not_applicable`,
all input tokens use the ordinary input price and the non-applicable cached component is exact zero.
Output cost uses every output token. Each component is calculated with decimal arithmetic from the
canonical manifest-number spelling, divided by 1,000,000, and rounded once to 12 decimal USD places
using round-half-even; arm components sum their already rounded row components and `total_usd` is
their exact sum. Serialized numbers must equal those quantized values. Redaction does not erase
known usage. Semantic counts disclose their judged denominator and do not extrapolate from partial
judgments.

V2 score atomically publishes exact `scored.jsonl` and `summary.json` sidecars together; the
scored ledger contains exactly one row for every terminal `RawAttemptV2`, in raw-ledger order, with
unique `raw_record_sha256`; no nonterminal row is scored. The summary binds both source raw bytes
and scored bytes. V2 report re-verifies the capsule, hashes the two sidecar files, proves that exact
ordered bijection, recomputes the summary from capsule raw plus scored rows, and refuses any field
mismatch before writing output. V1 serialization and behavior remain byte-compatible.

- Standalone score/report artifacts are sidecars, never capsule members. All six README quickstarts
  and the public-contract test migrate to `SCORE_DIR="${RUN_DIR}.score"` and
  `REPORT_PATH="${RUN_DIR}.report.md"`, then use `laconian score "$RUN_DIR" --output "$SCORE_DIR"`
  and `laconian report "$SCORE_DIR/scored.jsonl" --capsule "$RUN_DIR" --output "$REPORT_PATH"`.
  `score` and `report` reject an output equal to or contained by any prepared/sealed capsule. They
  cannot promote either raw format into a capsule.
- Old three-file run directories are reported as `legacy_run_directory`; no automatic migration
  invents missing plan, input, event, or executable provenance.
- Existing replay smoke data is regenerated as a capsule in tests.
- Directory names no longer define run IDs, so copied and renamed capsules verify identically.
- Capsule verification by a newer reader is distinct from resume, which requires the recorded
  producer/runtime fingerprint.
- PR 3 does not change `.gitignore` or imply that generated capsules are committed. Publication
  transport is specified in PR 6.

There is no released public benchmark artifact requiring evidence migration. The package remains
`0.1.0.dev0` until the capsule and attachment schemas stabilize.

## 20. Completion criteria

PR 3 is complete when:

- a provider cannot be constructed before an atomically published, verified capsule exists;
- every resume reads only bundled inputs and exact materialized plan rows;
- two cooperating mutators cannot execute the same pending request concurrently;
- every possible provider call has a durable pre-call attempt identity;
- missing results and returned errors with unknown delivery remain visible and cannot be retried
  into a favorable result;
- a crash after a committed result cannot cause that request to be repeated;
- `verify` is read-only and distinguishes valid incompleteness from corruption;
- copied or renamed capsules verify without their original checkout or working directory;
- required producer/runtime fingerprint drift blocks resume before credential access or provider
  construction;
- complete and intentionally blocked histories can be sealed without fabricating missing data;
- the sealed capsule exposes stable case, scenario, comparison, response, and protocol identities
  sufficient for later inference and judging attachments;
- no statistics, benchmark outcome, live API call, GitHub mutation, tag, release, or performance
  claim is created;
- focused, full, format, lint, type, package, public-contract, and replay capsule gates pass.

## 21. Follow-up boundaries

PR 4 consumes only a sealed generation capsule and creates immutable hard-scoring/inference
attachments. It defines generic pair estimands, scenario-clustered uncertainty, denominators,
cost accounting, and statistical versus claim-readiness outcomes without changing generation
bytes.

PR 5 creates blind semantic-judge, probability-sample human-audit, targeted critical-review, and

request contract.

PR 6 packages capsule plus selected attachments, bundled executable verifier, secret-scan result,

Corpus schema v2 and the dev/held-out/challenge commitment remain separate content work. The dev

confirmatory non-inferiority margin is selected independently, before confirmatory outputs, from
substantive quality and safety tolerance; it is not tuned from the pilot effect. Coverage and human
thresholds are likewise justified by precision and risk in their later bound protocols.
